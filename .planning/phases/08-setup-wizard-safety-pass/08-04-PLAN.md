<objective>
Run the safety checks a mapped repo needs before the daemon is allowed to spawn an agent against
it: a missing `CLAUDE.md`/`AGENTS.md` (the single highest-leverage success factor per research),
an unresolved remote or default branch (four other layers consume this recording per D-07), a
`.gitmodules` file (git's own docs call multi-checkout submodule support unsupported), and the
absence of branch protection on the default branch — server-side, and the one mitigation genuinely
outside a spawned agent's reach.

Purpose: this is the phase's "safety pass" half — SETUP-07 and SETUP-08 — and it operates on the
exact `Mapping[]` 08-03 produces, enriching it in place with the fields 08-05 needs to assemble
the final `Config`.

Output: `repo-safety.ts` exporting `annotateRepoSafety()`; every mapped repo's remote and default
branch recorded, every gap (missing docs, submodules, no branch protection) surfaced as a
prominent, actionable warning — never silent.

      control that survives even if the spawned agent circumvents local push guards; consider

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Wizard process → mapped repo's filesystem | Reading `CLAUDE.md`/`AGENTS.md`/`.gitmodules` and, on consent, writing a new `CLAUDE.md` — the repo is one the operator explicitly chose to map, so its contents are implicitly trusted per PROJECT.md's accepted-risk framing |
| Wizard process → GitHub API (`gh`) | Read-only `repo view` and branch-protection probes, using the operator's already-authenticated `gh` session from Plan 08-01's preflight |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-12 | Tampering | `checkAgentDocs` (starter-file generation) | medium | mitigate | Only ever writes when neither `CLAUDE.md` nor `AGENTS.md` exists and only after an explicit `confirm`; never overwrites an existing file under either name |
| T-08-13 | Information Disclosure | `annotateRepoSafety` (branch-protection probe) | medium | mitigate | A 404 (not found) and a 403 (insufficient permission) are both surfaced as the same conservative "protection absent or unknown" warning rather than guessing which, so a permission gap never gets reported as "protected" |
| T-08-14 | Tampering | `annotateRepoSafety` (submodule detection) | low | accept | A false negative (a submodule missed by the `.gitmodules` check, e.g. nested deeper than the repo root) is an accepted gap — documented in PITFALLS.md as a known limitation, not silently claimed as covered |
| T-08-15 | Denial of Service | `annotateRepoSafety` (per-repo loop) | low | mitigate | Every check is wrapped per-repo/per-check; one repo's `gh api` failure cannot abort checks for sibling repos in the same run |

No new package-manager install task exists in this plan — `execa` and `@inquirer/prompts` are
already sourced in `research/STACK.md`.
</threat_model>
