<objective>
Get the two — and only the two — secrets this project ever prompts for into a `.env` the daemon
can read, doing as much of the work as possible without bothering the operator: skip anything
already present and valid, lift the ngrok token out of its config file when it's there, and turn
a Linear key that can authenticate but cannot register webhooks into a message that names the
exact fix instead of a stack trace.

admin-confirmed) is also what Plan 08-03 reuses to list teams and projects — export it, don't make
08-03 re-validate.

(08-05) composes; a `.env` with mode 0600 holding exactly `LINEAR_API_KEY` and `NGROK_AUTHTOKEN`
when both are known.

    - Not present → prompt via `@inquirer/prompts`'s `password({ message, mask: true })` (never
      `input` — a plaintext-echoed API key is the failure mode this exists to prevent).
    - Whatever key is in hand, call `linearClient.viewer()`: throws/rejects → return a failure
      result with `fix: "Get a Linear personal API key from Settings → API → Personal API keys
      and re-run setup"` (never surface the raw SDK error).
    - `viewer()` succeeds, then call `linearClient.webhooks({ first: 1 })`: throws/rejects → the
      key is valid but not admin — return a failure result with `fix: "This Linear account is not
      a workspace admin, which webhookCreate requires. Ask a workspace admin to promote this
      account in Settings → Members, or generate a key from an admin account, then re-run setup"`
      (SETUP-03, D-06 — name the exact fix, not the GraphQL error text).
    - Both calls succeed → return `{ key, source: 'existing' | 'prompted', linearClient }` so the
      caller (and Plan 08-03) can reuse the already-authenticated client without re-prompting or
      re-validating.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator terminal → wizard process | The operator pastes a Linear API key and (if prompted) an ngrok authtoken; both are secrets from this point on |
| Wizard process → `~/.config/ngrok/ngrok.yml` | A file the ngrok CLI (a separate, already-trusted tool the operator installed) wrote; read-only access here |
| Wizard process → `.env` on disk | The one place both secrets persist between wizard runs and become readable by the daemon process |
| Wizard process → Linear GraphQL API | The `viewer()`/`webhooks()` calls leave the local machine over HTTPS to `api.linear.app` |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-04 | Information Disclosure | `acquireLinearKey`/`acquireNgrokToken` | critical | mitigate | `password()` prompt masks input; secrets are never passed to `console.log`/error messages, only masked previews if referenced at all |
| T-08-05 | Information Disclosure | `writeSecretsEnv` | critical | mitigate | `fs.chmod(path, 0o600)` runs unconditionally after every write, on create and on merge, so the `.env` is never left world- or group-readable |
| T-08-06 | Information Disclosure | `acquireNgrokToken` (yaml read) | medium | mitigate | Any yaml read/parse error is caught and logged as "not found" only — the file's contents (which include the secret) are never echoed in an error path |
| T-08-07 | Tampering | `acquireLinearKey` (admin probe) | low | mitigate | The admin-probe failure path returns a fixed, pre-written `fix` string rather than relaying the raw GraphQL error, which could otherwise leak internal Linear error detail into the terminal transcript an operator might paste into a support channel |
| T-08-08 | Spoofing | `acquireLinearKey` | low | accept | Whether a validated key belongs to the "right" Linear workspace is the operator's own responsibility — out of scope for a single-operator local tool |

No new package-manager install task exists in this plan — `@linear/sdk@93.0.1` (exact pin, T8) and
`@inquirer/prompts` are already sourced and versioned in `research/STACK.md`.
</threat_model>
