  <name>Task 1: Router — edge-detect on updatedFrom, re-fetch, emit DomainEvent</name>
  <files>src/ingress/router.ts, test/ingress/router.test.ts</files>
  <behavior>
    - Issue update whose updatedFrom contains an assigneeId key, and the freshly fetched
      issue's assignee is the bot: emits exactly one `issue.assigned`.
    - The same issue updated again (title changed, assignee untouched, assignee still the
      bot): emits nothing. This is ROADMAP criterion 5 and the single most important row.
    - Issue update whose updatedFrom contains an assigneeId key, and the freshly fetched
      issue's assignee is now someone else: emits `issue.unassigned`.
    - Payload says the assignee is the bot but the fresh fetch says otherwise: follows the
      fetch, not the payload, and emits nothing (INTK-05).
    - Issue action `create` with the bot pre-assigned: emits `issue.assigned` — there is no
      updatedFrom on a create, so key membership cannot be the test there.
    - Comment create: emits `comment.created` carrying issueId, commentId and parentId.
    - The fetch rejecting: logged with the delivery id, no event emitted, no throw escapes.
  </behavior>
  <action>
    Write `src/ingress/router.ts` exporting
    `createRouter(deps: { client: LinearClient; log: Logger; botUserId: string; onEvent: (e: DomainEvent) => void })`
    returning `{ enqueue(payload, deliveryId?: string): Promise<void> }`.

    `enqueue` runs entirely outside the request path — plan 03-05 calls it from a deferred
    callback after the 200 has been written. It must therefore never throw: wrap the body
    and log failures with the delivery id attached (assumption A1 makes that id the only
    correlation key across the two halves).

    Issue path, in two distinct steps:

    1. **Decide whether to look.** For action `update`, the edge is *key membership*:
       `payload.updatedFrom != null && "assigneeId" in payload.updatedFrom`. Keying instead
       on "the assignee is the bot" re-triggers on every subsequent edit of that issue
       forever, including the bot's own writes, which is loop surface 3 from PITFALLS. For
       action `create`, there is no prior-value object at all, so treat a pre-assigned bot
       on creation as the edge instead.
    2. **Decide what to do.** Re-fetch with `await client.issue(payload.data.id)` and read
       the assignee off the fetched issue. `updatedFrom` decided whether to look; it does
       not decide what happened. INTK-05 is absolute — the payload is a signal that
       something changed and never a source of truth, and this is also what makes the D-04
       poll able to reconstruct exactly the decision a lost delivery would have produced.
       Emit `issue.assigned` when the fresh assignee is the bot, `issue.unassigned` when
       the edge fired and the fresh assignee is not.

    Comment path: emit `comment.created` with `issueId`, `commentId` and `parentId` taken
    from `payload.data`. These are identifiers, not decisions — no branch is taken on
    comment content here, so INTK-05 is satisfied without a second fetch; the consumer
    re-fetches the body when it needs it. `parentId` is confirmed present on the Comment
    payload and is what Phase 6 needs for D-05 threaded-answer correlation.

    Attach `deliveryId` to every emitted event. Emit through `deps.onEvent` and stop —
    the phase boundary is a normalised `DomainEvent`, and anything the consumer does with
    it is out of scope. `DomainEvent` comes from `src/domain/types.ts`; record the exact
    union shape you rely on in `03-SUMMARY.md` under `Contract additions requested`.

    Write `test/ingress/router.test.ts` with `node:test` and `node:assert/strict`
    (01-CONTEXT D-12), against a fake `client` whose `issue()` returns a state that
    deliberately *differs* from the payload — a fake that echoes the payload back cannot
    detect a router that skipped the fetch, and INTK-05 is the thing under test. Cover
    every row in the behavior block. Do not run it.

  <action>
    Write `src/ingress/poll.ts` exporting
    `pollForMissedWork(deps: { client, store, botUserId, openQuestionIssueIds: string[] }): Promise<{ events: DomainEvent[]; watermark: string }>`.

    Read the watermark with `store.kvGet("poll_watermark")`, defaulting to the epoch. Query
    issues filtered on assignee equal to the bot and `updatedAt` greater than the
    watermark, and map each to the same `DomainEvent` shape the router emits — the poll
    exists so that a lost delivery becomes a latency problem rather than data loss, and it
    can only do that if it produces identical events (D-04). This coupling is load-bearing
    in the other direction too: D-08 drops null-actor events as untrusted, and that is only
    safe because this poll re-discovers them within five minutes.

    Then, for each id in `openQuestionIssueIds`, list comments created after the watermark
    and emit `comment.created` for each. D-05 exists because an issue-level diff cannot see
    a threaded answer — a comment is not an issue field, so without this pass a run sits in
    `awaiting_answer` until its deadline while the operator's reply is already in Linear.

    appends into the same connection and returns `this`, so collecting across iterations
    duplicates every earlier page.

    persists after the events are consumed; advancing it here would silently discard work
    if the process died between the query and the handling.
