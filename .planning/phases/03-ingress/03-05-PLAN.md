    1. Non-POST: 405 and return without reading the body.
    2. Capture `req.headers["linear-delivery"]` and the signature header

       drift in the log detail. Keeping the explicit comparison here is deliberate
       redundancy for diagnosis: without it the SDK's rejection is indistinguishable from a
       bad signature, which defeats D-09.
    6. **G2 — delivery id (HOOK-06, loop layer 4).** When the delivery header is present,
       use it. When it is absent, derive a surrogate as the sha256 of the raw buffer and
       log a one-time warning naming the header keys actually observed. This is a
       deliberate deviation from 03-RESEARCH § Example 1, which rejects outright: the
       header name rests on assumption A1, which no live delivery has yet confirmed, and a
       wrong guess there would reject 100% of real traffic. The surrogate degrades to a
       documented assumption instead of an outage, which is the project's stated
       reliability posture, and it dedupes correctly because Linear's retries resend the
       identical body. Record the deviation in `03-SUMMARY.md`.
       Insert with `store.tryInsertDelivery(id)`. A false return means the unique
       constraint fired: log guard `delivery-id:replay`, answer 200, and return. Answer
       200 rather than an error because a rejection burns Linear's retry budget on our own
       filtering. The insert is synchronous by design — an awaited dedupe write inside the
       acknowledgement path reintroduces the latency this whole plan removes.
    7. **G3-G5 — loop layers 1-3.** Call `selfEventGuards(payload, botUserId)` from
       `./guards.js`. On a drop: increment the counter with `incSelfEventDrop`, log the
       guard name, the delivery id and the returned `actorType`, answer 200, return.
    8. **Acknowledge.** Set 200 and end the response. Then, and only then, hand off with
       `setImmediate(() => router.enqueue(payload, deliveryId))`. Nothing below the
       acknowledgement is awaited. Per Pitfall 3 this ordering is the whole requirement:
       a handler that runs before the response adds directly to Linear's five-second
       budget, and the retries that follow are what auto-disable the webhook.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public ngrok URL → local listener | Fully untrusted; anyone can POST arbitrary bytes here |
| raw bytes → verified payload | `parseData()` is the authentication boundary; nothing above it may be trusted |
| verified payload → deferred router | Crossed after the acknowledgement, outside the request lifetime |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-19 | Spoofing | forged delivery to the public tunnel URL | critical | mitigate | HMAC over the received `Buffer` via `parseData()`; reject 400 with guard `signature` |
| T-03-20 | Tampering | signature bypass by re-serialising the body | critical | mitigate | Read the stream once into a Buffer and never reconstruct it (T14); fixtures sign the exact Buffer so the round-trip bug cannot pass (Pitfall 5) |
| T-03-21 | Spoofing | replay of a captured valid delivery | high | mitigate | SDK's ±60 s window **plus** an explicit presence assertion (T20), plus the delivery-id unique constraint |
| T-03-22 | Denial of Service | slow handler pushing the ACK past the 5 s budget, triggering retries that auto-disable the webhook | high | mitigate | Acknowledge before hand-off, enforced by a line-order gate, and a 1200 ms handler test asserting sub-200 ms ACK |
| T-03-23 | Information Disclosure | timing attack on the signature compare | low | mitigate | The SDK uses `timingSafeEqual`; do not reimplement |
| T-03-24 | Information Disclosure | request header values reaching the log via the diagnostic probe | medium | mitigate | `logFirstDeliveryShape` logs header *keys* only, never values |
| T-03-25 | Repudiation | every rejection class collapsing into one indistinguishable response | medium | mitigate | Per-guard names on all rejections (D-09), which is the specific capability the bundled handler helper cannot provide |
| T-03-26 | Denial of Service | rejecting all traffic if the delivery header name is wrong (assumption A1) | high | mitigate | sha256-of-body surrogate id with a one-time warning; the live-UAT item in Task 3 settles the header name |
