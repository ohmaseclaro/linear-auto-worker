  <behavior>
    - Fresh install: generates id and secret, writes both to kv, then registers.
    - Second boot: reads the same id and secret back from kv and generates nothing new.
    - Existing registration found by id: updates it, and never registers a second one.
    - Existing registration is disabled: the update carries `enabled: true` unconditionally.
    - Store write for the secret happens strictly before the first Linear API call.
    - Two pages of three nodes: the reconciler sees six webhooks, not nine.
    - A second webhook of ours with an ngrok URL and our label: deleted.
    - A webhook with an ngrok URL but a different label: untouched.
    - A webhook with a non-ngrok URL: untouched.
    - No value passed to the logger contains a secret.
  </behavior>
  <action>
    Write `src/ingress/registrar.ts` exporting
    `reconcile(client: LinearClient, store: Store, log: Logger, tunnelUrl: string): Promise<{ id: string; secret: string; url: string }>`.

    Order of operations, and the order matters:

    1. Build `desiredUrl` as `${tunnelUrl}/linear/webhook`.
    2. Read `webhook_id` and `webhook_secret` via `store.kvGet`. Fall back to
       `crypto.randomUUID()` and `crypto.randomBytes(32).toString("hex")`. Write both back
       with `store.kvPut` **before any call on `client`** — HOOK-03 and D-03. Per Unknown 3
       the API's returned secret field is typed nullable, so reading it back is code that
       works until it doesn't; generating locally is correct under both readings of
       Linear's contradictory docs. The client-supplied id is what makes registration
       idempotent across a URL that is different on every boot (D-01).
    3. Fetch `await client.webhooks({ first: 250 })`. Exhaust it with a while loop over
       `page.pageInfo.hasNextPage` awaiting `page.fetchNext()`, then read `page.nodes` once
       into `const all`. Do not collect nodes across iterations. Per T22 `fetchNext()`
       appends into the same connection and returns `this`, so per-iteration collection
       duplicates every earlier page; feed those duplicates to step 5 and it classifies
       this daemon's own live registration as a stray and deletes it. The reconcile snippet
       in `research/PITFALLS.md` does not paginate at all, so this loop is being written
       fresh with no prior art to copy.
    4. Find ours as `all.find(w => w.id === id)` — match on the persisted id, never on URL
       equality, because the URL is different every boot by design.
       - Absent: `client.createWebhook({ id, secret, url: desiredUrl, enabled: true, label: WEBHOOK_LABEL, allPublicTeams: true, resourceTypes: ["Issue", "Comment"] })`
         and throw when `.success` is false. Keep `resourceTypes` to those two — a narrower
         subscription is fewer loop surfaces for plan 03-03's guards to catch.
       - Present: `client.updateWebhook(id, { url: desiredUrl, enabled: true })`. One call
         does both halves of D-02. `enabled: true` is unconditional and is not a repair:
         with an ephemeral URL every restart guarantees failed deliveries, so Linear
         auto-disabling the webhook is the expected steady state.
       The SDK method names are `createWebhook`, `updateWebhook` and `deleteWebhook`. The
       GraphQL mutation spellings used in PROJECT.md, in 03-CONTEXT D-03 and in
       PITFALLS.md are not methods on `LinearClient` and `tsc` rejects them (T21). The
       verify gate greps for their absence.
    5. Prune (HOOK-09): for each entry in `all` where the id differs from ours, the label
       equals `WEBHOOK_LABEL`, and the URL matches `/\.ngrok(-free)?\.(app|dev|io)(\/|$)/`,
       log the id and URL then `deleteWebhook`. The label condition is a deliberate
       tightening of the research snippet, which matched on the ngrok URL pattern alone —
       03-RESEARCH's own prose requires that a foreign tool's ngrok webhook in the same
       workspace be left alone, and the label is the only field that can tell them apart.

    Export `WEBHOOK_LABEL = "linear-auto-worker"` from this module.

    Logging discipline: never pass the fetched array, a `Webhook` object, or anything
    derived from one wholesale to the logger. Per T23 the SDK's webhook fragment selects
    `secret`, so every element of that array carries a live signing secret and one
    structured log call writes all of them to disk. Log projected scalars — the id, the
    URL, the enabled flag — and nothing else. Also record `secret` for Phase 2's redaction
    list in `03-SUMMARY.md`.

    `kvGet(key): string | undefined` and `kvPut(key, value): void` are Store port methods.
    Record both in `03-SUMMARY.md` under `Contract additions requested`.

    Keep every trap reference in a comment that occupies its own line; the verify gate
    strips whole-line comments but not trailing ones.
  </action>

| daemon → Linear API | The signing secret crosses here once, outbound only |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
