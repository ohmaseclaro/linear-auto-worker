<objective>
Build the fan-out notifier: a structurally non-disableable log channel, a per-mapping
toggleable Linear comment channel that carries the self-event loop-prevention marker, and a
Slack channel that fires only on terminal states and questions — all wrapped in bounded
retry-with-backoff so a failing channel never fails the run and the notifier never throws
upward.

Purpose: DELV-05 and all six NOTF requirements live here. This is also the half of the
phase goal — "nothing that happens goes unlogged" — that the LinearClient facade (05-01)
does not itself guarantee; that guarantee is structural in how the channel array is built,
not a runtime check anyone could accidentally skip.
Output: `src/outbound/notify/{notifier,log-channel,linear-channel,slack-channel}.ts`, each
with a test file.

Note for the executor: same run-wide constraint as 05-01 — no `node_modules`, no build, no
test execution this phase. Every `<verify>` below is a static/structural grep check. Write
the test files completely and correctly; do not attempt to execute them.

Also note (informational, not a task for this plan): Phase 3 owns the actor/marker/
suppression-window/delivery-dedupe self-event filter that must be wired in before this
notifier is allowed to write to a live Linear workspace (ROADMAP.md's merge gate for this
phase). Nothing in this plan performs a live network call in its own verification, so that
gate is naturally respected here — it becomes binding at the Phase 7 integration gate.
</objective>

<task type="tracer" tdd="true">
  <name>Tracer: fan-out core — log always fires, a failing channel retries and never surfaces</name>
  <files>src/outbound/notify/notifier.ts, src/outbound/notify/log-channel.ts, src/outbound/notify/notifier.test.ts</files>
  <behavior>
    - emit() with only the always-on log channel configured writes exactly one structured
      entry for a 'picked_up' event, and that entry's fields include the run ID and the
      issue ID.
    - A second channel whose emit() rejects twice then resolves is retried with increasing,
      bounded delay (an injectable delay function makes this instant in a test), and the
      overall Notifier.emit() call still resolves once the channel succeeds.
    - A channel that always rejects still lets Notifier.emit() resolve — never reject — once
      its bounded attempt budget is exhausted, and a warning naming that channel is logged.
    - A caller that does real work inside a try, and calls notifier.emit(terminalEvent) in
      the matching finally, still produces exactly one terminal notification even when the
      try block throws partway through — proving the never-throws contract is what makes
      the finally-emission pattern safe.
  </behavior>
  <action>
    In notifier.ts define the shared `RunEvent` union and `NotifyChannel` interface. Every
    `RunEvent` variant carries `runId`, `issueId`, `issueIdentifier`, `issueUrl`, and `at`
    (epoch ms), plus a discriminant `kind` of `'picked_up' | 'worktree_ready' |
    'agent_started' | 'question_asked' | 'terminal'` (D-01's roughly-four-to-six milestones).
    The `'question_asked'` variant adds a `question: string` field. The `'terminal'` variant
    adds `state: 'delivered' | 'partial' | 'failed' | 'cancelled'`, `costUsd: number`,
    `tokensUsed: number`, an optional `prUrl: string`, and an optional short `reason:
    string` — never a full error object or agent transcript (DELV-05, NOTF-06).
    `NotifyChannel` is `{ name: string; enabled(e: RunEvent): boolean; emit(e: RunEvent):
    Promise<{ linearCommentId?: string } | void> }`.

    In log-channel.ts implement `LogChannel implements NotifyChannel`: `enabled()` always
    returns true — this channel takes no config and cannot be turned off (D-04). `emit()`
    writes one structured log entry per event carrying at minimum `runId`, `issueId`, and
    `kind` plus the event's other fields, and resolves; it never throws.

    In notifier.ts implement `Notifier`, constructed with a fixed channel array whose first
    entry is always a `LogChannel` instance — this ordering is what guarantees the log
    fires even if a later channel's constructor arguments are misconfigured. `emit(e)`
    invokes the log channel directly and unconditionally first, then for every other
    enabled channel runs a `withBoundedRetry(fn, options, delayFn)` helper (exponential
    backoff, a maximum attempt count, and a maximum single-delay cap — the bounded part of
    D-03 — with `delayFn` injectable so tests do not really wait), collects results with
    `Promise.allSettled`, and logs one warning naming the channel for every result still
    rejected after retries are exhausted. `emit()` itself never rejects. Return the
    `linearCommentId` from whichever channel's settled result carried one (none will yet —
    that arrives in Task 2 of this plan).
  </action>
  <verify>
    <automated>grep -q "withBoundedRetry" src/outbound/notify/notifier.ts && grep -q "allSettled" src/outbound/notify/notifier.ts && grep -q "runId" src/outbound/notify/log-channel.ts && grep -q "issueId" src/outbound/notify/log-channel.ts && test -f src/outbound/notify/notifier.test.ts</automated>
  </verify>
  <done>RunEvent/NotifyChannel contracts are defined; LogChannel always fires and is not config-gated; Notifier.emit() never rejects and retries other channels with bounded exponential backoff; the four behaviors above are encoded as tests in notifier.test.ts.</done>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker process → Linear comment content | Curated text composed from RunEvent fields, posted to a shared, human-visible Linear ticket |
| worker process → Slack incoming webhook | Outbound POST carrying a bearer-equivalent secret embedded in the URL itself |
| worker process → local log sink | Structured entries that must stay safe to grep and paste into a bug report |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-04 | Tampering | notify/linear-channel.ts | critical | mitigate | Self-event marker prefix is imported from Phase 3's single shared module (D-09), never redefined locally — a duplicated or wrong constant breaks Phase 3's loop-prevention and can amplify into a webhook loop that burns the shared Linear request budget. |
| T-05-05 | Information Disclosure | notify/linear-channel.ts | high | mitigate | Terminal and progress comments render from a curated per-kind template built only from RunEvent fields — never an agent's raw process output, a stack trace, or a filesystem path, any of which could carry a secret. |
| T-05-06 | Information Disclosure | notify/slack-channel.ts | medium | mitigate | Never log the full Slack webhook URL; log only a masked tail so a shared log file cannot leak the posting secret even if the log sink's redaction allowlist misses this field name. |
| T-05-07 | Denial of Service | notify/notifier.ts (retry-with-backoff) | medium | mitigate | D-03: bounded exponential backoff with a maximum attempt count and a maximum single-delay cap per failed channel per event, so a persistently-down Slack or Linear channel cannot retry indefinitely or make a healthy run look stalled. |
| T-05-08 | Repudiation | notify/log-channel.ts | low | accept | The non-disableable log channel already gives a complete audit trail for every transition (NOTF-01); a signed or tamper-evident log is not warranted for a single-operator local daemon. |

</threat_model>
