    - `recordDelivery(id, now)` returns `true` the first time and `false` for a second call

    - `insertRun()` followed by `updateRun(id, { state: 'preparing' })` followed by
      `getRun(id)` round-trips the new state — with no exception, no matter what string is
      passed as `state`, proving the store performs no transition validation of its own.
    - `listByState('queued', 'preparing')` and `nextQueued(limit)` return rows filtered and
      capped as named.
    - `insertQuestion()`, `openQuestionsForIssue()`, `expiredQuestions(now)` (rows whose
      `deadline_at < now` and `status = 'open'`), and `updateQuestion()` round-trip.
    - `appendRunEvent({ runId, from, to, at, detail })` followed by `listRunEvents(runId)`
      returns the event in insertion order.
    - `kvSet()`/`kvGet()` round-trips a string value.
    - A query against `sqlite_master` confirms `idx_runs_state` and `idx_questions_deadline_at`
      both exist.
    - Three sequential `insertRun()` calls against one handle (simulating three concurrent
      runs writing state, OPS-02's success criterion) all complete without a
      `SQLITE_BUSY`/locking exception.

  <action>
    Define and export a `Store` interface plus `createSqliteStore(db): Store` in
    `sqlite-store.ts`, built entirely on prepared statements against the handle plan 01's
    `openStore()` returns — no second connection, no separate pragmas.

    Runs: `insertRun(row)`, `getRun(id)`, `updateRun(id, patch)` (a generic column-by-column
    `UPDATE ... SET` built from whatever keys `patch` carries — never a hand-written list of
    "legal" fields to change, and never a check on what `patch.state` is allowed to be
    coming from), `findActiveRunByIssue(issueId)` (rows whose `state` is not null and not
    `'delivered'`/`'failed'`/`'cancelled'`, a *terminal-value* filter, not a transition
    check — distinguish the two explicitly in a comment, because CONTEXT.md's own written
    risk is exactly a future reader missing that distinction), `listByState(...states)`,
    `nextQueued(limit)` (rows with `state = 'queued'` ordered by `created_at`), `childRuns
    (parentRunId)`.

    Questions: `insertQuestion(row)`, `openQuestionsForIssue(issueId)` (join through
    `run_id` to filter by the question's own issue, or store `issue_id` denormalized on
    `questions` if that is simpler — either is fine, CONTEXT.md leaves the method surface to
    this plan), `findQuestionByCommentId(linearCommentId)`, `updateQuestion(id, patch)`
    (same generic-patch rule as `updateRun`), `expiredQuestions(now)`.

    Deliveries: `recordDelivery(deliveryId, receivedAt): boolean` — one
    `INSERT OR IGNORE INTO deliveries ...` followed by checking the statement's `changes`
    property, returning `changes > 0`. Never a `SELECT` first; that is exactly the race
    Pitfall 1 Layer 4 and Pitfall 4 both call out. `pruneDeliveries(olderThan)`.

    KV: `kvGet(key)`, `kvSet(key, value)` (`INSERT ... ON CONFLICT(key) DO UPDATE`).

    Run events (Phase 1 D-03 — this table is additive to the four
    `runs`/`questions`/`deliveries`/`kv` that `research/SUMMARY.md` originally named):
    `appendRunEvent({ runId, from, to, at, detail })`, `listRunEvents(runId)` ordered by
    `id`. Foundation only offers these two; deciding *when* to call them is Phase 6's job —
    `RunEngine.transition()` is the only caller this design expects.

    `transaction<T>(fn: () => T): T` wraps `db.transaction(fn)()`. `close()` calls
    `db.close()`.

    Write `sqlite-store.test.ts` per the behavior block using `node:test` and
    `node:assert/strict`, importing `openStore`/`runMigrations` from `./db.js`. **Write it;
    do not run it** (RUSH mode: nothing is installed). Commit with `git commit -n`.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Store CRUD surface -> every later phase (Phase 3 delivery dedupe, Phase 6 `RunEngine`, Phase 4 session-id persistence) | A store method that silently validates or rejects data hides bugs in whichever caller relies on it; a store method that lets a secret-shaped value ride through a returned row would defeat plan 01's redaction the moment that row is logged |
| Runtime-registered secrets (the webhook signing secret Phase 3 generates) -> Logger | A secret born after boot must reach the same redaction path as the two boot-time secrets, or D-05 only half-holds |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-05 | Information Disclosure | logger.ts / logger.test.ts | high | mitigate | `registerSecret()` extends the same scrub set used since boot; the written test proves a secret registered mid-process redacts from its first subsequent log line, not only secrets known at `loadFoundation()` time |
| T-02-06 | Tampering | sqlite-store.ts | medium | mitigate | `recordDelivery()` is one atomic `INSERT OR IGNORE` plus a `changes` check, never read-then-write, so two near-simultaneous deliveries sharing an id cannot both be accepted |
| T-02-07 | Repudiation | sqlite-store.ts | low | accept | `run_events` rows are appended by whoever calls `appendRunEvent()`; Foundation does not enforce that every mutation calls it. Phase 6's `RunEngine.transition()` is the enforcement point (Phase 1 D-03) — out of this phase's scope |
| T-02-08 | Elevation of Privilege | sqlite-store.ts | low | accept | `updateRun()` writes whatever `state` value it is given without checking transition legality, by design (CONTEXT.md risk 3). An out-of-band caller could write an illegal state; enforcing legality belongs to Phase 6's `RunEngine.transition()`, never to Foundation |
| T-02-SC | Tampering | npm install (continued use of better-sqlite3, pino) | high | accept | No new package is added in this plan; already covered by plan 01's `T-02-SC` row |
</threat_model>
