<objective>
The tracer for Phase 2: one path from a config file on disk to an open, migrated SQLite
handle to a logger that cannot leak what it was given, wired together in `loadFoundation()`.
Then the config side is filled out to its full validated shape.

Purpose: Foundation exists so that no other layer has to defend against a bad config file,
a database that blocks the event loop, or a secret that leaked into a log line. Proving the
three pieces wire together before either the store's full CRUD surface or the logger's
redaction edge cases are hardened (plan 02) catches an architectural mistake in this plan's
own commit, not spread across three later ones.
Output: `loadFoundation()` plus a fully validated `Config` loader; `sqlite-store.ts`'s CRUD
surface is plan 02's job, not this one's.

    - `loadFoundation()` calls `loadConfig()` first; a config read/parse failure throws
      before the database or logger are touched.
    - `openStore()` sets `journal_mode = WAL` and a `busy_timeout` before executing any
      migration SQL.
    - The migration runner reads `PRAGMA user_version`, applies only migrations numbered
      above it inside a transaction, and bumps the pragma — calling it twice against the
      same file is a no-op the second time.
    - `createLogger()` is called with whatever secrets are known at boot and returns an
      object exposing `child()`, `info()`, `warn()`, `error()`, `debug()`, and
      `registerSecret(value)` for a secret discovered later (the webhook signing secret,
      generated in Phase 3, does not exist yet at Foundation boot).
    - `loadFoundation()` returns `{ config, secrets, logger, db }` and is the only exported
      composition point — Phase 7's daemon boot calls this, not the four pieces separately.
  </behavior>

    `src/infra/store/db.ts` exports `openStore(dbPath): Database.Database` using
    `better-sqlite3`'s default export: construct the handle, `pragma('journal_mode = WAL')`,
    `pragma('busy_timeout = 5000')`, then run migrations — in that order, WAL and the
    timeout before any table exists (D-04, OPS-02). Export `runMigrations(db)` separately so
    plan 02's tests can call it directly: read `user_version` via
    `db.pragma('user_version', { simple: true })`, iterate an ordered list of migrations,
    and for each with `version` greater than the current value, run `db.exec(sql)` and bump
    `user_version` inside one `db.transaction()` call — a partial migration must never leave
    the pragma bumped without its SQL applied, or vice versa.

    `src/infra/logger.ts` exports a `Logger` interface (`child`, `info`, `warn`, `error`,
    `debug`) and `createLogger(initialSecrets: readonly string[])` returning a `Logger` plus
    `registerSecret(value: string): void`. Build exactly one `pino` instance, configured with
    a `formatters.log` hook that walks the log object recursively and replaces the value of
    any key matching `/(token|secret|key|authorization)/i` with `"[REDACTED]"` — this is the
    structural half of D-05, and it is what catches an object shaped like
    `{ authorization: '...' }` regardless of which call site produced it. Pair it with a
    custom write stream that string-replaces every known secret *value* (from
    `initialSecrets` plus anything added via `registerSecret`) with `"[REDACTED]"` before the
    line reaches stdout — this is the value-level half, and it is what catches a secret
    embedded inside an unrelated string (an error message quoting a failed request header,
    for instance), which a key-name-only redaction would miss. `child(bindings)` must return
    a wrapped logger sharing the same underlying pino child and the same secret set, so
    `logger.child({ runId, issueId })` (Phase 1 D-06 shape) inherits redaction for free
    rather than needing its own setup.
