<objective>
Complete the worktree lifecycle around the tracer's thin `prepareWorktree` /
`removeWorktree`: collision suffixing, the per-repo mutex, the success/failure removal
policy, and the boot reconcile.

This is the plan that makes ROADMAP Phase 4 success criterion 1 true — two runs against
the same repository proceeding simultaneously without touching each other or the
operator's working copy.

Purpose: a worktree is where every commit the agent makes lands. Every failure mode in
this file is silent at the time it happens and surfaces minutes later as something else —
a detached HEAD surfaces at push time, a reset branch surfaces as vanished work, a
contended index lock surfaces as a random `git` failure on the *other* run.

  <name>Task 1: Collision suffixing, the per-repo mutex, and the removal policy</name>
  <files>src/execution/worktree.ts, src/execution/worktree.test.ts</files>

  <behavior>
    `worktree.test.ts`, `node:test` + `node:assert/strict`, with a scripted `runCommand`
    that records every argv it was handed:
    - A free branch name is used verbatim — `issue.branchName` is never slugified,
      lowercased, or otherwise rewritten.
    - When the scripted `git` reports the branch already exists, the created branch is
      `<branchName>-2`; when `-2` also exists, `-3`. Assert on the argv actually passed to
      `worktree add`, not on a return value.
    - No argv the scripted runner ever receives contains the branch-resetting variant of
      the create flag.
    - `symbolic-ref -q HEAD` is invoked against the new worktree path after creation, and
      a non-zero exit from it makes `prepareWorktree` reject.
    - The worktree path is under the daemon root and contains neither `mapping.repoPath`
      as a prefix nor a `..` segment.
    - Two `prepareWorktree` calls against the same `repoPath` do not interleave their
      `git` invocations: with a runner that resolves on an external promise, assert the
      second call issues no argv until the first has finished. Two calls against
      *different* repo paths do interleave.
    - `finishWorktree` with a `delivered` verdict issues `worktree remove --force`;
      with `partial` and with `failed` it issues nothing.
  </behavior>

  <action>
    Expand `src/execution/worktree.ts`. Keep the exported signatures plan 04-01 fixed;
    add `finishWorktree(o: { verdict, repoPath, path, runCommand })`.

    **Collision suffixing (D-11, AGNT-01).** Before creating, probe whether the branch
    exists (`git -C <repoPath> show-ref --verify --quiet refs/heads/<branch>` or
    equivalent) and, while it does, try `<branchName>-2`, `-3`, and upward. Suffix; never
    reuse. The capital-B force variant of the create flag resets an existing branch to the
    base commit and destroys the previous attempt's commits — the entire reason D-11 names
    it. Carry that as a comment so it is not reintroduced by someone reaching for the
    "obvious" idempotent create.

    Bound the search (a few dozen attempts) and throw a named error rather than looping
    forever, because the probe is a subprocess call and an unbounded loop here is an
    unbounded fork bomb against the operator's repo.

    **Per-repo mutex (Pitfall 6).** `git` takes a repository-wide `index.lock`, so two
    simultaneous `fetch` / branch-create sequences against one repository fail randomly,
    and the failure surfaces on whichever run lost the race — not the one that caused it.
    Serialize preparation per `repoPath` with an in-process promise-chain mutex keyed by
    the resolved absolute path: a `Map<string, Promise<unknown>>` where each new
    preparation chains onto the previous one and the entry is cleaned up when the chain
    drains. Different repositories must still run in parallel — the whole point of
    criterion 1 is two simultaneous runs, and a global lock would serialize the daemon.
    Keep it in-process: the tunnel singleton rule already establishes that this daemon is
    one process, and a lockfile would be a second, weaker mechanism for the same job.

    **Fetch before create.** `git -C <repoPath> fetch --quiet <remote>` inside the mutex,
    so the worktree branches off a current base rather than whatever the operator last
    pulled. A fetch failure is not fatal to a run whose base already exists locally — log
    it and continue rather than refusing to work offline.

    **Removal policy (AGNT-02).** `finishWorktree` removes on `delivered` only. A
    `partial` or `failed` run leaves the worktree exactly where it is, because that
    directory is the only artifact the operator can take over in, and because a failed run
    whose evidence was deleted is indistinguishable from a run that never started.
    `git worktree remove` refuses a dirty tree, so the removal passes `--force`; that is
    the one place in this phase where a force flag is correct, and it is correct because
    the tree being removed is one this daemon created and has already judged delivered.

    Update the test file per the behavior block. **Write it; do not run it.**
    Commit with `git commit -n`.
  </action>

  <name>Task 2: Boot reconcile — prune orphans, report worktrees that vanished</name>
  <files>src/execution/worktree.ts, src/execution/worktree.test.ts</files>

  <behavior>
    Added to `worktree.test.ts`:
    - Given a scripted `git worktree list --porcelain` output containing three worktrees
      under the daemon root and a set of non-terminal run rows referencing only one of
      them, `reconcileWorktrees` removes exactly the two unreferenced ones and returns
      them as `pruned`.
    - A worktree that is **not** under the daemon root is never removed, even when no run
      row references it — the operator's own worktrees are not this daemon's to delete.
      Assert the argv for that path was never issued.
    - A run row whose recorded worktree path is absent from the porcelain listing comes
      back in `orphanedRuns` and no `git` command is issued for it.
    - `git worktree prune` is issued before the listing is read, so stale admin files left
      by a crash do not appear as live worktrees.
    - Parsing handles the porcelain format's record separation (blank-line-delimited
      records, `worktree <path>` / `HEAD <sha>` / `branch <ref>` or `detached` lines) and
      a path containing a space.
  </behavior>

  <action>
    Add `reconcileWorktrees(o): Promise<{ pruned: string[]; orphanedRuns: string[] }>` to
    `src/execution/worktree.ts` (AGNT-03). It takes the injected `runCommand`, the
    `daemonDir`, the list of mapped repository paths, and the caller's list of
    `{ runId, worktreePath }` for every non-terminal run row. It does not read the
    database itself — Phase 7 calls it at boot with rows it already has, and keeping the
    query out of this module is what lets the whole thing be tested with no SQLite.

    Sequence per mapped repository:
    1. `git -C <repoPath> worktree prune` first. A crashed process leaves stale
       administrative files that make a deleted directory still list as a worktree; prune
       clears them so step 2 sees reality.
    2. `git -C <repoPath> worktree list --porcelain`, parsed into records. Write the parser
       against the porcelain format rather than the human format — the human format's
       columns are not stable and a path with a space silently mis-splits.
    3. For each listed worktree **under the daemon root** with no non-terminal run row
       referencing it: `worktree remove --force`, and collect the path into `pruned`.
       The daemon-root check is the safety property here. Compare resolved absolute paths
       with a trailing separator, not with a bare `startsWith` on the raw string — `/a/bc`
       must not match a root of `/a/b`.
    4. For each run row whose path is absent from the listing: collect the run id into
       `orphanedRuns` and issue nothing. The run row is a database fact and this module
       does not write state (Phase 6 owns transitions); returning it is how the caller
       learns to fail that run with a diagnosis rather than replaying it. Note the
       neighbouring hazard in the summary rather than acting on it: T18 and T26 say a
       `running` row surviving to boot means an unclean exit and must be failed, never
       requeued, because its push status is unknowable.

    Never remove the main working tree, and never remove a worktree outside the daemon
    root. Both are one condition, and it is the condition that keeps a bug in this
    function from deleting the operator's work.

    Extend the test file per the behavior block. **Write it; do not run it.**
    Commit with `git commit -n`.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Daemon-owned worktree root -> operator's filesystem | This module is the only thing in the product that issues a recursive forced delete; a path-containment bug here deletes the operator's work |
| Linear-supplied `branchName` -> a filesystem path and a git ref | Attacker-influenceable text becomes a directory name and a ref name |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-09 | Destruction of data | worktree.ts reconcile | critical | mitigate | Removal is gated on resolved-absolute-path containment under the daemon root with a trailing separator, never a bare string prefix; the main working tree is never a removal candidate |
| T-04-10 | Destruction of data | worktree.ts create | high | mitigate | The branch-resetting create variant is never emitted (D-11); a colliding branch is suffixed, so a retry cannot discard the previous attempt's commits |
| T-04-11 | Tampering | worktree.ts | medium | mitigate | `git` is invoked through the injected argv-array runner (`execa`), never a shell, so a crafted `branchName` cannot escape into a command. `git` itself rejects refs containing `..`, control characters and a leading `-`, and a create that git rejects fails the run loudly |
| T-04-12 | Denial of Service | worktree.ts | medium | mitigate | The collision probe is bounded and throws a named error rather than looping; the per-repo mutex is keyed per repository so one busy repo cannot stall the others |
| T-04-13 | Information Disclosure | worktree paths | low | accept | Worktree paths embed the Linear branch name, which embeds the issue identifier and a slug of its title. They live under the daemon-owned root on the operator's own machine; no new disclosure surface |
| T-04-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs nothing. `worktree.ts` imports only `node:path`, `node:fs/promises` and types; the command runner is injected |
</threat_model>
