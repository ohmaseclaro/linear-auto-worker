    `stream-parser.test.ts`, `node:test` + `node:assert/strict`, pure:
    - **The bug D-08 names:** one known event pushed as two chunks split *mid-token* —
      inside a string value, not at a convenient boundary — yields exactly one event, deep
      equal to the original. Then the same event split at three arbitrary offsets, driven
      by a loop over every offset in the serialized string, all yielding one event. The
      loop is the test: a single hand-picked split point proves the case that happened to
      be chosen.
    - Several events in one chunk yield several events, in order.
    - A chunk ending exactly on a newline leaves nothing in the carry; the next chunk
      starts a fresh event.
    - Blank and whitespace-only lines are skipped without reaching `onEvent` or `onBad`.
    - An unparseable line reaches `onBad` with the line text, does not throw, and **does
      not stop the events after it from being delivered** — assert the count after the bad
      line, because a parser that silently stops is the failure that looks like a hung run.
    - `flush()` emits a trailing event with no newline, and emits nothing when the carry is
      empty. Calling `flush()` twice emits once.
    - Replaying `fixtures/stream-events.jsonl` through the parser in randomly-sized chunks
      (a fixed seeded sequence of sizes, so the test is deterministic) yields exactly the
      event count the fixture contains, in order.
  </behavior>

  <action>
    Finish `src/execution/stream-parser.ts` around Pattern 3's implementation. Keep it a
    pure factory: `makeLineParser(onEvent, onBad)` returning `{ push(chunk: string),
    flush() }` with a `carry` string. It imports nothing but types, does no I/O, and knows
    nothing about event shapes — that knowledge belongs to the router and putting it here
    would make the parser untestable without it.

    Two details that are the difference between correct and nearly correct:
    - Search for the newline with `indexOf` from the start of the carry and slice, in a
      loop, rather than splitting the whole buffer. Splitting reallocates the entire carry
      on every chunk, and a real run's stdout is megabytes.
    - `flush()` must clear the carry after emitting, so a second call is a no-op. A double
      flush on an error path otherwise duplicates the terminal event, and the duplicate
      terminal event is the one that would make a run look like it delivered twice.

    Guard the carry against unbounded growth: if it exceeds a generous ceiling with no
    newline in it, report the situation through `onBad` and reset, rather than growing
    until the process dies. A single line that large is not an event; it is a malfunction,
    and a parser that OOMs takes the whole daemon with it.

    **`src/execution/fixtures/stream-events.jsonl`.** One real event per line, in the
    emission order `04-RESEARCH.md` records: the `system/hook_started` and
    `system/hook_response` pairs that precede `system/init` (their existence is the entire
    proof behind D-04 and T4), then `system/init` carrying the verbatim key list including
    `skills`, `permissionMode`, `session_id` and `tools`, then an `assistant` event with a
    `tool_use` content block, a `system/task_summary` with a `detail` string, a `user`
    event with a `tool_result`, a `system/post_turn_summary` with `status_category`,
    `status_detail` and `needs_action`, and a terminal `result` event carrying every field
    of the `ResultEvent` interface — `structured_output`, `total_cost_usd`,
    `permission_denials`, `usage`, `modelUsage`, `stop_reason`, `terminal_reason`.

    Build it from the verbatim key lists, field names and real values in `04-RESEARCH.md`,
    which were copied off the wire in the research session. Do not invent field names: a
    hand-written fixture encodes the author's assumptions, which is exactly what these
    tests exist to catch. Where the research gives a real value, use that value. Note in
    the summary that re-capturing this fixture from a live run at the integration gate
    would strengthen it, and that it is currently a faithful transcription rather than a
    capture.

    Every event in the fixture must carry `session_id` and `uuid`, including the first one
    — that is the observed property D-04 depends on.

    Write `stream-parser.test.ts` per the behavior block. **Write it; do not run it.**
    Commit with `git commit -n`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Agent stdout -> worker memory | Everything the parser sees is emitted by a process whose instructions came, in part, from attacker-influenceable ticket text |
| Agent stdout -> the run's observable facts | The router is what turns bytes into "this run delivered"; a wrong reading here is a wrong outcome reported to a human |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-21 | Denial of Service | stream-parser.ts | high | mitigate | The carry has a growth ceiling and resets through `onBad` rather than growing until the daemon OOMs; a single unparseable line is skipped, not fatal |
| T-04-22 | Spoofing | event-router.ts | high | mitigate | The GSD assertion throws rather than logs, so a session without the GSD install cannot produce work that is reported as GSD's; the echoed `permissionMode` is a second independent detector |
| T-04-23 | Repudiation | event-router.ts | medium | mitigate | The denial tally records `tool_name` and `decision_reason_type` per denial, so "produced nothing" is always attributable to a named refusal rather than unexplained |
| T-04-24 | Information Disclosure | event-router.ts | medium | mitigate | The router passes progress strings out through a callback and formats nothing; per ASVS V7 raw agent output and stack traces are never posted outward, and redaction is the log sink's job (Phase 2) |
| T-04-25 | Tampering | event-router.ts | low | accept | Agent-authored `structured_output` is attacker-influenceable in content but is validated against `AgentResultSchema` by the verdict module (plan 04-05) before anything acts on it |
| T-04-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs nothing. Both modules are pure; the parser imports only types and the router imports only `src/domain/` and types |
</threat_model>
