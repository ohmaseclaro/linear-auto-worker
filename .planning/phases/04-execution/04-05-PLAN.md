      assertion.
    - When `isAlive` returns false after SIGINT, no SIGTERM and no SIGKILL are sent.
      Liveness is checked, not assumed.
    - The handle's own kill method is never invoked — assert the fake handle's kill spy has

    - `runAgent` resolves after the escalation completes even though the fake child promise

      pipe and the promise stays pending forever, so completion must be a race between the
      promise and the escalation, never the promise alone.
    - The resolved outcome carries `timedOut: true` and the escalation step that finally
      worked, and **no worktree operation is performed** — assert `runAgent` issues no
      removal of any kind (AGNT-08: the worktree stays intact).
    - Both streams are consumed: pushing chunks into the fake stderr while stdout is also
      producing does not stall stdout, and stderr content reaches the logger (D-07).
    - stdout chunks reach the injected line parser in order, including a chunk arriving
      after the deadline but before the process dies.
    - A child that exits normally before the deadline cancels the timer — assert the fake
      `kill` was never called and that no timer keeps the test alive.
    - A `system/init` assertion thrown by the router aborts the run: the escalation runs
      immediately rather than at the deadline, and the thrown error propagates out of
      `runAgent`. Failing loudly must not mean waiting 45 minutes to fail loudly.
  </behavior>

  <action>
    Finish `src/execution/supervisor.ts` around the signature plan 04-01 fixed. Keep every
    OS interaction injectable — `spawn`, `kill`, `isAlive`, `sleep` — because the
    escalation is exactly the logic that cannot be tested against a real process without
    becoming flaky, and it is exactly the logic that must not be wrong.

    **The spawn.** `detached: true`, `stdio: ["pipe","pipe","pipe"]`, `reject: false`,
    `cwd` at the worktree, `env` from `buildChildEnv`. `detached` makes the child a
    process-group leader, verified `pgid === pid`, and that is what makes the negative-pid
    form legal (D-09). `reject: false` is required so a signalled process does not throw
    past the evidence-based verdict; if it throws, D-06 is violated by accident.

    **The escalation (AGNT-08, D-10 amended, T29).** On the deadline:
    SIGINT to the negative pid, wait ~15s, check liveness; if alive, SIGTERM to the
    negative pid, wait ~10s, check liveness; if alive, SIGKILL to the negative pid.
    Each `process.kill(-pid, sig)` is wrapped so an ESRCH from an already-dead group is not
    an error — the race between the check and the signal is normal, not exceptional.

    Three comments here are load-bearing:
    - Why SIGINT is first and why it is not sufficient: it keeps the session resumable, so
      an overrun run can be continued rather than only killed — but it was measured to kill
      only the group leader while a backgrounded grandchild survived. SIGTERM to the same
      group killed both. The escalation is mandatory, not a courtesy.
    - Why the pid is negated: a signal to the positive pid orphans the agent's own Bash
      subprocesses, which then accumulate across a week.
    - Why the handle's own kill method is never called: even detached, it orphans the
      grandchild and leaves the promise permanently pending, because the survivor holds the
      stdout pipe.

    **Completion is a race**, not an await. `Promise.race` the child handle against the
    escalation's completion, and resolve on whichever finishes. Awaiting the handle alone
    is Pitfall 3 — a run stuck in `running` at 0% CPU forever.

    **The drain (D-07).** Consume stdout and stderr concurrently, both started before
    either is awaited. Undrained stdout deadlocks at ~64 KB, which a real run reaches in
    its first minute; draining stdout only moves the deadlock to stderr. stdout feeds the
    line parser feeding the router; stderr goes to the log at debug level, never further —
    raw agent output is not posted outward (ASVS V7).

    Use execa's own API surface for all of it. There is no `.on()` on this handle (T30);
    write against `pid`, `kill`, `stdout`, `stderr`, `then` and `catch`.

    **Do no worktree work.** A timed-out run's worktree stays exactly where it is; the
    supervisor does not know about worktrees and must not learn. Removal is
    `finishWorktree`'s job and it is verdict-gated (plan 04-02).

    **Fail fast on the init assertion.** When the router throws — an absent GSD install, a
    wrong echoed permission mode — trigger the escalation immediately rather than at the
    deadline, and let the error propagate. Waiting out a 45-minute timeout to report a
    fault detected in the first second is the difference between a loud failure and a slow
    one.

    Take the deadline from config (`Config.defaults`, the max-run-time toggle) with a
    documented default. Note in a comment that the 45-60 minute figure is inherited and
    unmeasured, and that too short truncates real work into `partial` rather than losing
    it — a stated assumption, not a verified number.

    Write `supervisor.test.ts` per the behavior block. **Write it; do not run it.**
    Commit with `git commit -n`.

  <behavior>
    `verdict.test.ts`, pure — every case built from a fixture-shaped result event and a
    hand-built evidence object. **Every single case uses an exit code of 0 and
    `is_error: false`**, because that is what every failure mode in this project actually
    produces, and a test suite that varies the exit code is testing a signal the product
    does not use.
    - **D-06, the barren case:** no commits, no working-tree changes, `subtype: "success"`,
      `terminal_reason: "completed"`, exit 0 → `failed`. This one case is the phase's
      whole thesis.
    - Commits present, run completed → `delivered`.
    - Commits present, run truncated (`error_max_turns`, or the supervisor's `timedOut`
      flag) → `partial`, and the returned object says a draft PR should still ship.
    - Uncommitted working-tree changes but no commits → `failed`, with the uncommitted
      paths carried on the result so the operator is told the work exists but was never
      committed. Silently discarding that is how an agent's hour disappears.
    - **QA-01 / D-16:** `structured_output.status === "needs_input"` → `needs_input`,
      carrying both `question` and `assumption`, and it **wins over the evidence** — a run
      that committed something and still asked a question is a question, because the answer
      changes what the rest of the work should be.
    - A `needs_input` with a question but no assumption fails validation and is reported as
      a malformed agent result, not silently accepted. D-16 requires **both**; a question
      with no assumption is a run that cannot proceed without a human, which is the outcome
      the assumption exists to avoid.
    - `structured_output` that does not satisfy `AgentResultSchema` is rejected and
      classified from the evidence alone, with the schema error carried through. The agent
      is not trusted to be well-formed.
    - **T31:** a result whose `stop_reason` is a tool use — which is what a resumed session
      returns — classifies identically to one whose stop reason is a completed turn.
      Assert both, so a stop-reason check reintroduced later fails here.
    - A non-empty `permission_denials` is surfaced as a distinct cause on the result, with
      the tool names, alongside whatever the verdict is.
  </behavior>

  <action>
    Finish `src/execution/verdict.ts`. Pure: it takes the collected evidence and the
    collected result event and returns a classification. It runs no git commands — the
    caller collects `git log --oneline <base>..HEAD` and `git status --porcelain` and
    passes them in. Keeping it pure is what makes it exhaustively testable with no git
    binary present, which under RUSH mode is the only kind of test that exists.

    Classification order (D-06), and the order is the requirement:
    1. A valid `needs_input` structured output wins over everything.
    2. Commits present and completed → `delivered`.
    3. Commits present and truncated → `partial`. A partial run still ships a **draft** PR;
       this is why `partial` is a real state in the binding contract rather than a rounding
       of `failed` (Phase 1 D-01).
    4. Otherwise → `failed`. Research names this shape `barren`; the binding nine states
       have no such literal and it folds into `failed`.

    Validate `structured_output` against `AgentResultSchema` imported from
    `src/domain/agent-result.js` before acting on any field of it. It is the one input to
    this module authored by an agent that was itself steered by attacker-influenceable
    ticket text; treating it as typed because TypeScript says so is exactly the mistake the
    schema exists to prevent. On a validation failure, carry the error and classify from
    evidence alone.

    Three rules here are silent bugs if broken, and each needs its comment:
    - **The exit code is not an input.** Do not accept it as a parameter. Every
      silent-failure probe in the research session exited 0 with `is_error: false`,
      `subtype: "success"` and `terminal_reason: "completed"` (T1, D-06). A function that
      cannot see the exit code cannot be tempted by it.
    - **Read the parsed object the result event already carries**, not the string field
      beside it. The parse is duplicated work and a second failure mode for no gain (T31).
    - **Do not gate on the stop reason being a completed turn.** With `--json-schema` it is
      a tool use, verified twice, and a resumed session returns a tool use as well — so
      such a check is a bug that fires on every answered question (T31).

    Surface `permission_denials` as a first-class cause on the returned object with the
    tool names attached. `barren` plus a denial naming `Write` is a diagnosable failure with
    a one-line fix in `agent-args.ts`; `barren` alone is a mystery.

    Also carry `total_cost_usd` and `num_turns` through onto the result. Phase 5's terminal
    comment reports them, and reporting raw input tokens instead would be actively
    misleading — the cost is dominated by cache creation on the ~61k-token GSD system
    prompt, not by the ticket.

    Write `verdict.test.ts` per the behavior block. **Write it; do not run it.**
    Commit with `git commit -n`.
