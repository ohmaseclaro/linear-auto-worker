Complete the agent invocation surface: the flag list, the child environment, and the
prompt trust boundary — plus the tests that make each of the three quiet
misconfigurations fail loudly if anyone reintroduces them.

`04-CONTEXT.md`'s `<specifics>` is the whole brief for this plan: **all three `claude -p`

it.** A test suite that only proves the happy path is worth nothing here, because the

nothing and reports success is worse than a crash, and three separate flag mistakes all
produce exactly that.

operator-facing trust document.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Linear issue text -> agent prompt | Any workspace member can file an issue; its title and body become instructions to an agent with shell and filesystem access on the operator's machine. The highest-severity boundary in the milestone. |
| Worker process env -> spawned child env | The worker holds both secrets; the child must hold neither, whatever the ambient environment contains |
| Mapped repository -> spawned session | The repo's own `.claude/settings.json` hooks execute unprompted |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-14 | Elevation of Privilege | prompt.ts | critical | mitigate | Both D-14 layers, each with its own test: C0/C1, zero-width, bidi and Unicode-tag stripping, plus an untrusted-data delimiter whose closing form is neutralized inside the body so a ticket cannot escape it |
| T-04-15 | Information Disclosure | agent-env.ts | critical | mitigate | Allowlist from `{}`, tested against a deliberately polluted environment including an invented `CLAUDE*` variable no denylist could have known |
