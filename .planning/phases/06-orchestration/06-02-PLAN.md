<objective>
Expand the tracer's engine into the full pickup, cancellation and failure surface. Three
things here are ordering or arity constraints rather than features, and each has a specific
failure the operator would misdiagnose:

- **Ack before work (D-09).** A cold repo's `git fetch` takes seconds. Acknowledging after
  it means a ticket that sits visibly untouched for long enough that the operator assigns
  it somewhere else. This is an ordering constraint, not a performance target.
- **Edit, do not re-post (D-10).** A queue-position comment re-posted on every position
  change turns one ticket into a wall of bot noise.
- **Exactly once (D-13, OPS-04).** No retry loop. A second attempt on a run whose branch is
  already pushed produces a second PR for work that already shipped.

Purpose: make the run's non-happy paths as deliberate as its happy path.
Output: `run-engine.ts` covering pickup, cancel and terminal failure, plus its test file.

## Two places the research contradicts the locked decisions — the decisions win

1. `ARCHITECTURE.md`'s transition table contains a `failed -> queued` row described as
   "bounded auto-retry, cap 2". **Do not build it.** D-13 and OPS-04 lock a single attempt
   with no retry loop. If you find yourself writing an `attempt` counter with a threshold,
   you are building the rejected design.
2. `ARCHITECTURE.md` uses stale state names. The nine binding literals are `queued`,
   `preparing`, `running`, `awaiting_answer`, `delivering`, `delivered`, `partial`,
   `failed`, `cancelled`. Translate: `claimed`/`worktree_ready` -> `preparing`,
   `agent_running` -> `running`, `done` -> `delivered`, `abandoned` -> `cancelled`,
   `barren` -> `failed`.

  <name>Task 1: Pickup — acknowledge, subscribe and show position before any git work</name>
  <files>src/orchestration/run-engine.ts, src/orchestration/run-engine.test.ts</files>

  <behavior>
    - Handling `run.requested` calls, in this order and before the worktree port is touched
      at all: insert the run at `queued`, post the acknowledgement comment, set the issue to
      In Progress, add the operator as a subscriber.
    - A fake worktree port that throws if called records zero calls until after all four of
      the above have happened. This is the ordering assertion; write it as a spy that fails
      the test on early invocation rather than as a comment.
    - When no slot is free, the acknowledgement body carries the queue position from
      `scheduler.positionOf()`.
    - A position change updates the **same** comment id: the fake Linear client records one
      create and N updates, never two creates, across three position changes.
    - The stored ack comment id survives being read back, so a restart can still edit rather
      than re-post.
    - A failure to post the acknowledgement does not abort the run — it is logged and the run
      proceeds (a notification channel must never fail a run).
  </behavior>

  <action>
    Extend `handle()` in `run-engine.ts` for the `run.requested` path.

    Order is the deliverable (D-09, INTK-02, invariant 12). Insert the run row at `queued`,
    then acknowledge on the ticket, then move the issue to In Progress, then add the
    operator as a subscriber (INTK-03 — assignee-based pickup takes the ticket out of the
    operator's "Assigned to me" view for the whole run, so without the subscription the
    operator loses sight of their own ticket). Only after all of that may the engine reach
    for the worktree or agent ports. Ten seconds is the budget; the ordering is what makes
    it achievable, since the four calls above are Linear API calls and a cold `git fetch`
    is not.

    Structure it so the ordering is hard to undo rather than merely documented: put the
    acknowledgement sequence in a named function that returns the ack comment id, and make
    the worktree/agent path take that id as a parameter. Then work cannot start without the
    acknowledgement having happened, because there is nothing to pass it.

    Persist the returned comment id on the run row (or in `kv` keyed by run id — record
    which under `Contract additions requested`). Every later position update **edits that
    comment** (D-10, INTK-06). Never post a second position comment; a queue that moves
    three times must leave exactly one comment on the ticket. Read the position from
    `scheduler.positionOf()` — plan 01 made it side-effect free precisely so this call site
    can be made from anywhere.

    The acknowledgement is a notification, and a notification failing must never fail a run:
    wrap the ack sequence so a Linear error is logged and swallowed, with the run continuing
    at `queued`. Note in the summary that a swallowed ack means the position comment has no
    edit target, so the position update must no-op rather than fall back to posting.

    Write the ordering assertions into `run-engine.test.ts` per the behavior block.
    **Write it; do not run it.** Commit with `git commit -n`.
  </action>

<task type="auto" tdd="true">
  <name>Task 2: Cancellation from every non-terminal state, and failure attempted exactly once</name>
  <files>src/orchestration/run-engine.ts, src/orchestration/run-engine.test.ts</files>

  <behavior>
    - `run.cancelled` from `queued`, `preparing` and `awaiting_answer` moves the run to
      `cancelled` immediately and releases whatever it held (a `queued` run holds nothing; an
      `awaiting_answer` run holds no slot but does hold an open question, which is closed).
    - `run.cancelled` from `running` or `delivering` does **not** transition. It records a
      cancel-requested flag and returns; the run reaches `cancelled` only when the supervisor
      reaches its next checkpoint and reads the flag.
    - `run.cancelled` from `delivered`, `partial`, `failed` or `cancelled` is a no-op — no
      transition, no error thrown, and the terminal state is unchanged.
    - Cancelling twice from `running` leaves one flag and produces one eventual transition.
    - A run entering `failed` posts one diagnosis carrying the error and the log path, and
      the worktree and branch cleanup ports are **not** called.
    - There is no code path anywhere that moves a run out of `failed`. A test drives a run to
      `failed` and asserts a subsequent tick, poll or scheduler pass leaves it there.
    - The terminal notification is emitted from a `finally`, so a throw inside the delivering
      path still produces exactly one terminal emission.
  </behavior>

  <action>
    Cancellation (D-11, INTK-08). Drive it from the domain state table rather than a
    hand-written list: a state that is not terminal accepts cancel. Split on whether the
    state has a live child — the state table already records that per D-02. States with no
    live child transition to `cancelled` now. States with a live child set a
    cancel-requested flag on the run row and return, because a pushed branch cannot be
    un-pushed and an instant transition would claim something that did not happen. Expose a
    `isCancelRequested(runId)` read the supervisor checkpoint consults. Setting the flag is
    idempotent.

    Terminal failure (D-13, OPS-04). Failure is final. On entering `failed`, post one
    diagnosis comment carrying the error and the path to the run's log, and leave the branch
    and the worktree in place for the operator to inspect — deliberately do not call the
    worktree cleanup port on this path. Build no retry: no attempt counter with a threshold,
    no requeue-on-transient-class, no back-off. `ARCHITECTURE.md` describes a bounded
    auto-retry; it is superseded. The one legitimate way a failed run runs again is the
    operator reassigning the ticket, which arrives as a fresh `run.requested`.

    Emit the terminal notification from a `finally` covering the whole run body (invariant
    11), so a crash, a throw in the delivering path, or a rejected push all still produce
    exactly one terminal emission. Silence on failure is the loudest complaint in this
    product category.

    Slot release also belongs in that `finally`, and plan 01 made the release function
    idempotent so the `finally` can run after a path that already released.

    Extend `run-engine.test.ts` per the behavior block. **Write it; do not run it.**
    Commit with `git commit -n`.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Linear webhook -> engine cancel path | An unassignment event, once routed, drives a run out of the state machine; a spoofed or replayed one would cancel real work |
| Engine -> Linear diagnosis comment | Error text produced inside the daemon is published to a ticket that anyone in the workspace can read |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-06 | Information Disclosure | run-engine.ts failure path | high | mitigate | The diagnosis comment carries the classified failure reason and the log **path**, never the log body and never a raw serialized SDK error — those routinely carry request headers and therefore the API key |
| T-06-07 | Spoofing | run-engine.ts cancel path | medium | transfer | Cancel authenticity is Phase 3's obligation: signature verification, actor identity and delivery-ID uniqueness gate what reaches `handle()`. The engine trusts the routed event by design; record this reliance in the summary |
| T-06-08 | Denial of Service | run-engine.ts pickup path | medium | mitigate | Acknowledgement failures are swallowed rather than throwing, so a Linear outage degrades ticket visibility instead of stalling the queue |
| T-06-09 | Tampering | run-engine.ts terminal path | high | mitigate | No code path leaves `failed`, so a replayed event cannot cause a second attempt and therefore a second PR against an already-pushed branch |
| T-06-10 | Repudiation | run-engine.ts cancel path | low | mitigate | The cancel-requested flag and the eventual transition both append `run_events` rows, so a cancel that was requested but never honored is visible |
| T-06-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs no packages; it imports only `src/domain/` and Node builtins |
</threat_model>
