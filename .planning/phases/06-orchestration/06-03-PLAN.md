<objective>
The question lifecycle: posted, correlated, deadlined, and durable across a restart.

The mechanism is **exit-and-resume** (D-04, T11). An MCP `ask_human` tool that long-polls
is the obvious design and it is wrong in a way that produces no visible symptom: Claude Code
backgrounds any main-conversation MCP call still running past roughly two minutes, hands the
model a task id, and the model **keeps coding without the answer** — shipping a confidently
wrong PR that looks fine until review. There is no in-process wait anywhere in this plan.
The child is already gone by the time a question exists.

Two design rules here carry the phase's remaining bug density:

- **The deadline is data, not a timer.** Absolute epoch milliseconds in SQLite, swept by a
  tick. A restart erases a timer, and the timeout fallback is the one mechanism the whole
  "never fragile" posture depends on — if it can be erased, a run can wait forever.
- **Correlation is threaded-first with a top-level fallback.** Replying in the main comment
  box instead of the thread is the mistake everyone makes, and silently ignoring it is
  indistinguishable from the bot being broken.

Purpose: make an hours-long human wait cost nothing and survive anything.
Output: `questions.ts` with correlation, the sweep, and the per-mapping toggles, plus tests.

  <name>Task 1: Correlate an answer to its question — threaded first, top-level fallback</name>
  <files>src/orchestration/questions.ts, src/orchestration/questions.test.ts</files>

  <behavior>
    - A comment whose `parentId` equals a stored `linear_comment_id` correlates to that
      question, even when the issue holds several open questions.
    - A top-level comment (no `parentId`) on an issue holding **exactly one** open question
      correlates to it.
    - A top-level comment on an issue holding **two** open questions correlates to neither and
      is reported as ambiguous rather than guessed at.
    - A top-level comment on an issue holding **zero** open questions correlates to nothing.
    - A comment authored by the bot correlates to nothing, whichever tier it would match.
    - Correlation is order-independent: given two open questions created a minute apart, a
      threaded reply to the **older** one resolves the older one. A test asserts this
      explicitly — recency-based correlation would resolve the newer and is the exact bug
      that appears the day two runs are open on one ticket, which is normal once multi-repo
      lands, not exotic.
    - A correlated answer marks the question `answered`, records the answering author, and
      asks the engine to move the run back to `running` with the answer as resume input.
    - Applying an answer to a question already `answered` or `expired` is a no-op.
  </behavior>

  <action>
    Implement `correlate(comment, openQuestionsForIssue)` in `questions.ts` as a pure
    function returning a match, an ambiguity, or nothing — pure so the tests above are cheap
    and so plan 04's boot recovery can reuse the identical logic on comments it lists from
    Linear rather than re-deriving a second, divergent correlation path.

    Tier 1 (D-06, QA-04): `comment.parentId === question.linearCommentId`. This is the
    correct path and works with any number of open questions.

    Tier 2 (D-06): a top-level comment with no parent, on an issue holding exactly one open
    question. Anything else — two or more open questions, or none — matches nothing. The
    fallback exists because replying in the main box rather than the thread is the mistake
    everyone makes; the exactly-one guard is what stops the fallback from becoming a guess.

    Correlate by stored comment id and never by recency (invariant 13). SQLite is the source
    of truth and Linear comments are a projection: do not re-parse comment bodies to recover
    which question is which, because Linear's own documentation notes comments are editable.

    Drop bot-authored comments at the top of `correlate`, before either tier. Phase 3 filters
    self-events at ingress with four independent guards, but boot recovery (plan 04) feeds
    this function comments it listed directly from the API, which did not pass through those
    guards — so this check is not redundant, it is the guard for the second entry point.

    Treat the answer body as **untrusted data, never as instructions**. Carry it through as
    an opaque string, do not interpolate it into anything the orchestrator itself interprets,
    and record in the summary that the resume-prompt composition in Phase 4 owns delimiting
    it and stripping control and zero-width characters (AGNT security criterion 6). Do not
    build that stripping here — record the obligation so it cannot fall between the phases.

    `applyAnswer` transitions only questions in `open`; anything else returns without effect,
    so a replayed delivery cannot resume a run twice.

    Write `questions.test.ts` per the behavior block. **Write it; do not run it.**
    Commit with `git commit -n`.
  </action>

<task type="auto" tdd="true">
  <name>Task 2: The durable deadline sweep, and the per-mapping question toggle</name>
  <files>src/orchestration/questions.ts, src/orchestration/questions.test.ts</files>

  <behavior>
    - Opening a question writes `deadline_at` as an absolute epoch-millisecond value computed
      from a clock injected as a dependency, defaulting to four hours out.
    - A mapping specifying its own question deadline overrides the default; a mapping
      specifying nothing inherits it (sparse override, Phase 1 D-09).
    - `sweep(now)` with `now` before the deadline does nothing.
    - `sweep(now)` with `now` past the deadline marks the question `expired`, posts the stated
      assumption to the ticket, and asks the engine to return the run to `running` with the
      assumption as resume input (QA-05).
    - **The restart test (QA-06, invariant 8):** construct a questions module, open a question,
      discard the module entirely, construct a fresh one over the same store, and sweep past
      the deadline — it still expires. Nothing about the deadline lived in the discarded
      instance. Write this as an explicit test; it is the assertion that proves the deadline
      is data.
    - Sweeping twice past the deadline expires once and resumes once.
    - A question answered before its deadline is not expired by a later sweep.
    - With the question flow disabled for the mapping (QA-07), `needs_input` writes no
      question row, does not enter `awaiting_answer`, posts the assumption to the ticket, and
      continues on it — the run keeps its slot throughout, because it never blocked.
  </behavior>

  <action>
    Deadlines (D-05, QA-06, invariant 8). Store `deadline_at` as an absolute epoch-millisecond
    integer on the `questions` row. Compute it at open time from an injected clock — inject
    it rather than reading the wall clock inline, so the expiry tests are deterministic
    instead of sleeping.

    Expose `sweep(now)` and let Phase 7 drive it from the daemon's periodic tick. Nothing in
    this module registers a timer callback of any kind: a scheduled callback is process-local
    state, and a restart silently erases it, leaving a run to wait forever on a fallback that
    no longer exists. That is why the deadline is a column and expiry is a query for rows
    whose `deadline_at` has passed and whose status is still `open`.

    Default four hours, overridable per mapping via the sparse override shape Phase 1 D-09
    fixed. Resolve the value at open time and store the resulting absolute timestamp, not the
    duration — then a config edit does not retroactively move a deadline already announced on
    a ticket.

    On expiry: mark the row `expired`, post the assumption to the ticket so the record shows
    what was decided rather than leaving the operator to infer it from the diff, and resume
    the run through the engine exactly as a real answer would, with the assumption text in
    place of the answer. Expiry and answering converge on one resume path — two paths would
    drift.

    Make the sweep idempotent by transitioning the question status inside the same operation
    that selects it, so a second sweep finds no `open` rows past the deadline.

    Question flow disabled per mapping (QA-07): the branch is taken at `needs_input`, before
    any question row is written. Post the assumption, resume immediately on it, and leave the
    run in `running` — it never blocked, so it never released its slot and never re-acquired
    one. Keep this branch visibly adjacent to the blocking branch in the same function so the
    difference between them is one `if` and not two subsystems.

    Extend `questions.test.ts` per the behavior block, including the discard-and-reconstruct
    restart test. **Write it; do not run it.** Commit with `git commit -n`.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Linear comment body -> question answer -> agent resume input | The primary untrusted-input boundary of this phase. Text authored by any workspace member (and, via boot recovery, fetched without passing ingress's guards) becomes input to a process running with the operator's shell |
| Question correlation -> run resumption | Deciding which run an answer belongs to is an authorization decision in disguise: correlate wrongly and one ticket's answer steers another ticket's run |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-11 | Elevation of Privilege | questions.ts correlation | critical | transfer | Answer text is carried as opaque data and never interpreted by the orchestrator. Delimiting it as untrusted and stripping control and zero-width characters is Phase 4's prompt composition (AGNT criterion 6); this plan records the obligation in its summary so it cannot fall between the two phases |
| T-06-12 | Spoofing | questions.ts tier 2 fallback | high | mitigate | The top-level fallback fires only when exactly one question is open, and bot-authored comments are dropped before either tier — so the fallback cannot silently absorb an unrelated or self-authored comment |
| T-06-13 | Tampering | questions.ts correlation | high | mitigate | Correlation reads the stored `linear_comment_id`, never comment recency and never the comment body, so editing a comment after the fact cannot re-target an answer |
| T-06-14 | Denial of Service | questions.ts sweep | high | mitigate | The deadline is a stored absolute timestamp swept by a tick, so no run can wait indefinitely on a fallback a restart erased; and a blocked run holds no slot, so open questions cannot exhaust the semaphore |
| T-06-15 | Repudiation | questions.ts expiry | medium | mitigate | Expiry posts the assumption it proceeded on to the ticket, so the record shows what was decided rather than requiring the operator to infer it from the diff |
| T-06-16 | Information Disclosure | questions.ts | low | accept | Question and assumption text originate from the agent working on that ticket and are posted back to the same ticket; no cross-ticket disclosure path exists |
| T-06-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs no packages; it imports only `src/domain/` and Node builtins |
</threat_model>
