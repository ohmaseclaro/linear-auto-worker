    it has a live child. Import that table from `src/domain/state-machine.js` and derive the
    answer from it. Do not write a set of quoted state literals into `scheduler.ts` — a
    second list is a second thing to keep in sync, and the sync failure is the one that

    `handle(event)` covering only `run.requested` and `question.answered` for now.

    `transition()` is the single choke point and does three things atomically per Phase 1
    D-03: validate the move against the domain transition table, write `runs.state`, and
    append a `run_events` row (`run_id`, `from`, `to`, `at`, `detail`). A transition that

    and asks the engine to transition to `awaiting_answer`; `applyAnswer(questionId,
    answer)` marks the row answered and asks the engine to transition back to `running`.
    It calls `engine.transition()` and never writes `runs.state` itself.

  <name>Task 2: Complete the semaphore — queue order, position, pause, and the starvation test</name>
  <files>src/orchestration/scheduler.ts, src/orchestration/scheduler.test.ts</files>

  <behavior>
    `scheduler.test.ts` asserts:
    - **The starvation test (QA-03, D-02, the reason this phase exists):** with a cap of 3,
      putting three runs into `awaiting_answer` leaves `inUse() === 0` and a fourth run is
      admitted immediately. This test failing means the daemon dies on three open questions.
    - A run in each slot-holding state counts exactly one slot; a run in each terminal state
      counts none. Drive this from the domain state table so adding a state cannot silently
      escape the assertion.
    - `acquire()` beyond the cap does not resolve until a release happens; releases hand the
      slot to the longest-waiting run (FIFO).
    - Calling a release function twice credits the semaphore once.
    - `positionOf(runId)` returns 1-based position for a waiting run and 0 for an admitted
      one; the position of the run at the head decreases as earlier runs are admitted.
    - After `pause()`, no further acquisition resolves; `start()` resumes the queue in order.
    - N runs derived from one ticket occupy N slots, not one (D-03).
  </behavior>

  <action>
    Finish `scheduler.ts` around the tracer's core (INTK-06: a configurable global cap
    defaulting to 3).

    FIFO wait queue: `acquire()` returns immediately when a slot is free, otherwise parks a
    resolver in order. Add `positionOf(runId): number` — 1-based place in the wait queue,
    0 once admitted. Plan 02 consumes this for the "queued, position N" comment, so it must
    be a plain query with no side effects.

    `pause()` stops admitting (parked waiters stay parked, they are not rejected); `start()`
    resumes. Phase 7 calls `pause()` first in the shutdown sequence.

    Recount, don't accumulate: derive `inUse()` from the set of admitted run ids the
    scheduler holds, and expose a `syncFromStore(runs)` that recomputes that set from the
    runs table by asking the domain state table which of their states hold a slot. Plan 04's
    boot recovery calls it after its sweep so the semaphore starts a process agreeing with
    the database rather than at zero.

    `awaiting_answer` gets no special-case branch anywhere in this file. It holds no slot
    because the domain state table says it holds none, and the scheduler asks the table.
    That is the whole implementation, and it is deliberately the whole implementation.

    Write `scheduler.test.ts` per the behavior block. **Write it; do not run it.**
    Commit with `git commit -n`.

| Linear comment text -> run engine | Answer bodies authored by humans (or by anything that can comment on the workspace) cross into the orchestrator here and are carried toward an agent prompt |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Denial of Service | scheduler.ts | critical | mitigate | Slot-holding is derived from the domain state table, so `awaiting_answer` cannot hold a slot by construction; the starvation test asserts three blocked runs leave three slots free |
| T-06-02 | Denial of Service | run-engine.ts | high | mitigate | Release is idempotent and called from a `finally`, so a throwing transition cannot leak a slot permanently |
| T-06-03 | Tampering | run-engine.ts | high | mitigate | `runs.state` has one writer; `transition()` validates against the domain transition table and throws rather than writing an illegal state |
| T-06-04 | Repudiation | run-engine.ts | medium | mitigate | Every transition appends a `run_events` row in the same operation, so a state change that was not recorded is a missing row rather than a missing log line |
| T-06-05 | Information Disclosure | questions.ts | low | accept | Question and assumption text originates from the agent and is posted back to the ticket it came from; no new disclosure surface in this plan |
| T-06-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs no packages. Orchestration imports only `src/domain/` and Node builtins (`node:test`, `node:assert/strict`). If an install becomes necessary, stop and route through the package legitimacy gate |
