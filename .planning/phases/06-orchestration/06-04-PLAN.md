<objective>
Everything a restart has to put right, plus the poll that makes a lost webhook a latency
problem rather than a correctness problem.

Two things here are easy to get subtly wrong and expensive to diagnose:

**Recovery is per-state (D-07), and it is not the uniform requeue the research recommends.**
`queued` and `preparing` requeue — nothing was spent. `running` and `delivering` **fail with
a diagnosis** — an agent session and a partial push cannot be safely resumed blind, and
re-running risks a second pull request for work that was already pushed. `awaiting_answer`
simply persists, because plan 03 put its deadline in a column rather than in a timer, so
there is nothing to re-arm. Nothing is left as a zombie with a stuck In Progress ticket
(D-08).

**The comment-listing half of the poll is the one people leave out.** An issue-level diff
sees that an issue changed but not that the change was a threaded reply on a comment. Without
listing comments on issues holding open questions, a run that was answered five minutes after
the daemon died sits in `awaiting_answer` for the full four hours anyway. This obligation is
stated in `03-CONTEXT.md` D-05 and is **shared** with Phase 3 — Phase 3 owns the issue-level
watermark poll; this plan owns the comment half and the correlation of what it finds.

Purpose: make a restart lossless where it can be and honest where it cannot.
Output: `recovery.ts` with the boot sweep and the reconciliation poll, plus its test file.

## The research says the opposite of D-07 on one point — D-07 wins

`.planning/research/SUMMARY.md` invariant 7 reads: *"Every `agent_running` row found at boot
is a crash artefact — requeue with `resumable = true`; never trust the row."*
`ARCHITECTURE.md`'s transition table agrees, and its shutdown sequence writes
`state=queued + resumable=true` on SIGTERM.

**06-CONTEXT D-07 supersedes this for the boot path.** A `running` or `delivering` row found
at boot is **failed with a diagnosis**, not requeued. Build D-07.

The two are reconcilable and it is worth understanding why, because it tells you what you are
protecting: a *clean* shutdown (Phase 7's `drain`) is what marks its children `queued` before
exiting, and that path stays lossless. A `running` row that survives to boot therefore means
the daemon did **not** shut down cleanly — it crashed, was killed, or lost power — and in that
case the worktree's contents and whether anything was pushed are both unknown. Requeueing
blind is what produces a second PR for work already shipped. Record this reconciliation in
your summary; Phase 7 owns the clean-shutdown half and needs to know this half assumes it.

The nine binding `RunState` literals are `queued`, `preparing`, `running`, `awaiting_answer`,
`delivering`, `delivered`, `partial`, `failed`, `cancelled`. `ARCHITECTURE.md` uses an older
vocabulary; translate rather than copy.

    - Each failed run receives exactly one diagnosis naming the recovered-from state, and its
      worktree cleanup port is not called.
    - Each requeued run's In Progress ticket state is left as it is — the run is going to run,
      so the ticket is still correctly In Progress.
    - A run in `awaiting_answer` has nothing re-armed: no timer is registered, and its
      `deadline_at` is unchanged after the sweep.
    - Sweeping twice is a no-op the second time.
    - After the sweep, the scheduler's `inUse()` agrees with the recovered rows — a run left in
      `awaiting_answer` contributes zero.

    `engine.transition()`, preserving the sole-writer rule (invariant 6) and getting the

    scheduler and the same reasoning applies: a second list is a second thing to keep in sync.

    - `running`: transition to `failed` with a diagnosis naming the recovered-from state.
    - `delivering`: transition to `failed` with a diagnosis naming the recovered-from state.
    - `awaiting_answer`: leave it entirely alone. Its deadline is a column and its question row

    - Terminal states are not loaded and not touched.

      transition.

      through ingress's guards, so this is the guard).
    - The watermark advances only after a successful pass; a Linear error mid-poll leaves it
      where it was, so the next pass re-covers the same window rather than skipping it.
    - A Linear failure during the poll is logged and swallowed — the daemon stays useful and
      merely misses backlog until the next pass.

  <action>

    interval; this module only exposes it.

    Half one — missed assignments (INTK-07). Query Linear for issues assigned to the bot with
    `updatedAt` greater than the watermark held in `kv`, and enqueue any that have no
    non-terminal run. This is the recovery path that makes an ephemeral tunnel URL safe:
    between the daemon dying and the webhook being re-registered on the next boot, Linear is
    delivering to a URL that will never come back, and those deliveries are lost. Polling for

    from any cached payload (invariant 2).
