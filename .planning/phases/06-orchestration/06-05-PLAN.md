<objective>
One ticket, several repos. The whole design rests on one property: **the parent's status is
derived from its children and never stored** (D-12, Phase 1 D-04). That is not a
normalisation preference — it is precisely what stops one repo's failure from discarding
another repo's shipped pull request (DELV-07). A stored parent status can disagree with its
children, and the disagreement resolves in whichever direction the last writer happened to
run.

The rejected alternative is one session with `--add-dir` across all repos. It fails four
ways: the concurrency cap stops meaning what it says (one slot holding four repos' worth of
context, when the cap exists to bound local RAM); a failure in repo B loses repo A's finished
work because they share a state row; one process with several worktrees invites commits to
the wrong repo and a pull request against the wrong remote; and delivery is per-repo anyway —
one branch, one push, one PR.

Purpose: make partial success the normal, unremarkable case.
Output: `fanout.ts` with the sub-run plan and the derived status, wired into the engine's
pickup path, plus its test file.

  <behavior>
    - `planSubRuns(issue, mapping)` for a mapping with one repo returns a single run with no
      parent — the single-repo path is not wrapped in a degenerate parent.
    - For a mapping with three repos it returns one parent and three children, each child
      carrying its own repo, branch, worktree path and pre-assigned session id, and each child
      naming its parent.
    - Child branch names are distinct across repos, so two children of one ticket cannot
      collide on a shared branch name.
    - `deriveParentStatus(children)` returns, for a set of child states:
      all `delivered` -> `delivered`;
      at least one `delivered` and at least one `failed` -> `partial`;
      all `failed` -> `failed`;
      all `cancelled` -> `cancelled`;
      any child still non-terminal -> the parent is still in flight, reported as such rather
      than as a terminal state.
    - **The DELV-07 assertion:** a parent with one `delivered` child holding a pull request
      URL and one `failed` child derives `partial`, and reading the parent does not alter,
      clear or reclassify the delivered child's pull request URL. Write this as an explicit
      test — it is the failure the whole design exists to prevent.
    - `deriveParentStatus` is pure and called on read: a test calls it twice over the same
      children and asserts nothing was written anywhere in between.
  </behavior>

  <action>
    Write `src/orchestration/fanout.ts` as two pure functions plus their types. Pure because
    everything interesting about this design is a total function from children to a status,
    and purity is what makes "never stored" enforceable rather than merely intended.

    `planSubRuns(issue, mapping)` resolves the mapping's `repos[]` and returns the run rows to
    insert. One repo returns one run with no parent — do not wrap the common case in a parent
    of one. N repos return one parent (kind `ticket`) and N children (kind `repo`), each child
    carrying its own repo directory, branch, worktree path and pre-assigned session id, and
    each naming its parent.

    Each child is a first-class run (D-03). It gets its own state, its own worktree, its own
    `claude` process, and therefore its own concurrency slot. Plan 01's scheduler counts runs
    rather than tickets, so this requires nothing new from the semaphore — but say so in your
    summary, because the cap exists to bound local RAM and a design where N repos cost one
    slot would quietly break the thing the cap is for.

    `deriveParentStatus(children)` maps child states to the parent's reported status per the
    behavior block. The parent run row carries **no state column value** (D-12, Phase 1 D-04).
    If the schema requires the column to be non-null, record under `Contract additions
    requested` that the parent row needs it nullable, or a `kind` discriminator that makes the
    column inapplicable — and do not work around it by writing a state you would then have to
    keep in sync, which is the exact failure this decision exists to avoid.

    Note the `partial` mapping in your summary: `partial` in the contract means a run that
    shipped something incomplete, and here it also means a ticket where some repos shipped and
    some did not. Both readings answer "did this ship anything" with the same query, which is
    what Phase 1 D-01 chose the state vocabulary for.

    Also record — do not build — the ticket brief the architecture recommends: one brief per
    child worktree naming the issue, the full repo list, and which repo that child owns, so
    each child knows it is part of a coordinated change. Composing and writing it into the
    worktree is Phase 4's prompt work; this plan only supplies the repo list. Do not build
    cross-run agent messaging; for a single-operator tool that is speculative complexity.

    Write `fanout.test.ts` per the behavior block, including the DELV-07 partial-success
    assertion. **Write it; do not run it.** Commit with `git commit -n`.
  </action>

  <name>Task 2: Fan out at the engine's pickup, and report per-repo outcomes independently</name>
  <files>src/orchestration/run-engine.ts, src/orchestration/fanout.test.ts</files>

  <behavior>
    - `run.requested` for a ticket mapped to three repos inserts one parent and three children
      and enqueues the three children; the parent is never enqueued and never acquires a slot.
    - Plan 02's acknowledgement ordering still holds: the ack, the In Progress transition and
      the subscription happen once for the ticket, before any worktree port is reached, and
      not once per child.
    - Three children occupy three slots against a cap of three, and a fourth unrelated run
      waits (D-03).
    - A child reaching `failed` emits its own terminal outcome and does not transition, cancel
      or clean up its siblings — a test drives child A to `delivered` and child B to `failed`
      and asserts child A's run row and pull request URL are untouched (DELV-07).
    - Cancelling the ticket cancels every non-terminal child using plan 02's per-state cancel
      rules, and leaves already-terminal children as they are.
    - The children run in parallel, subject only to the global semaphore — there is no
      sequencing between them.
  </behavior>

  <action>
    Wire `planSubRuns` into `run-engine.ts`'s `run.requested` path, immediately after plan 02's
    acknowledgement sequence and before anything reaches the worktree port. Fan-out happens at
    the engine, never inside an agent session.

    The acknowledgement is per **ticket**, not per child: one ack comment, one In Progress
    transition, one subscription, then the children. Do not move the ack inside the per-child
    loop — that ordering constraint is plan 02's and it still binds.

    Enqueue only the children. The parent is a row, not a runnable thing: it never acquires a
    slot, never gets a worktree, never spawns a process.

    Per-repo independence is the deliverable (DELV-07). Each child's terminal handling is
    plan 02's existing terminal path, unchanged and per child. Deliberately do **not** add a
    sibling-cancellation, sibling-cleanup or fail-fast path — a child failing must have no
    effect on its siblings, and the fastest way to reintroduce the bug this phase is guarding
    against is a well-intentioned "abort the rest on first failure".

    Read the parent's status through `deriveParentStatus` wherever the ticket-level outcome is
    needed. Never write it. If you find yourself wanting somewhere to cache it, that is the
    disagreement D-12 forbids.

    Cancellation of the ticket enumerates the children and applies plan 02's per-state cancel
    rules to each: non-terminal children with no live child process transition at once, those
    with one get the cancel-requested flag, terminal ones are untouched. The parent needs no
    cancel handling of its own, because its status is derived from exactly those children.

    Notification shape: notify per child, and once at ticket level with the full list — Slack
    gets one message per child plus a rollup, Linear gets a rollup to avoid spamming the issue.
    Emitting is Phase 5's; record the two event shapes this plan needs under `Contract
    additions requested`.

    Extend `fanout.test.ts` per the behavior block. **Write it; do not run it.**
    Commit with `git commit -n`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Config mapping -> N spawned runs | A single ticket's mapping determines how many concurrent agent processes are created; the mapping is operator-authored but its arity is the input to the RAM bound |
| Child run -> sibling child run | Children share a ticket and a parent row but must share no failure path; the boundary between them is what protects a shipped pull request |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-23 | Tampering | fanout.ts derived status | critical | mitigate | The parent status is a pure function of its children with no writer anywhere, so parent and children cannot disagree and one repo's failure cannot reclassify another repo's delivered pull request |
| T-06-24 | Denial of Service | run-engine.ts fan-out | high | mitigate | Each child is a first-class run against the semaphore (D-03), so a ticket mapped to many repos is bounded by the global cap rather than multiplying past the RAM budget the cap exists to enforce |
| T-06-25 | Tampering | fanout.ts branch naming | medium | mitigate | Child branch names are distinct per repo, so two children of one ticket cannot collide on a shared branch and overwrite each other's work |
| T-06-26 | Elevation of Privilege | run-engine.ts fan-out | medium | transfer | Which repositories a ticket may touch is entirely determined by the operator-authored mapping; ticket text never selects a repo. Record this reliance so Phase 8's wizard keeps mapping authorship out of ticket content |
| T-06-27 | Repudiation | run-engine.ts fan-out | low | mitigate | Each child transitions through `engine.transition()` and appends its own `run_events` rows, so a per-repo outcome is individually reconstructable |
| T-06-SC | Tampering | npm/pip/cargo installs | high | accept | This plan installs no packages; it imports only `src/domain/`, sibling orchestration modules, and Node builtins |
</threat_model>
