tree to a clean typecheck.

attribution — plan 01's inventory is the only map — so work the clusters, not the
timeline.

    Collect every requested addition from every phase SUMMARY. Deduplicate: two phases
    asking for the same store method under different names is the common case, and
    merging them into one method is the whole point of doing this centrally.

    For each surviving request, choose one disposition and record it in
    `07-CONTRACT-RECONCILIATION.md` with the requesting phase, the requested signature,
    the disposition, and one line of reasoning:
      - ADD — the need is real and no existing member covers it. Add it to the right
        domain file with the requester's semantics, not a guessed generalisation.
      - MAP — an existing member already covers it under a different name. Do not add;
        note the member the caller should use. Plan 03 fixes the call site.
      - REJECT — the request violates a locked decision. Say which one.

    Three rejections are already decided and must be applied on sight if requested,
    because each one un-decides something 01-CONTEXT locked one-way:
      - Anything that gives the Store knowledge of the state machine. The Store is a dumb
        typed repository (02-CONTEXT specifics) and the RunEngine is the only writer of
        `runs.state` (06-CONTEXT D-01).
      - A stored status column on a parent run row. Parent status is derived from children
        (01-CONTEXT D-04) precisely so the two cannot disagree.
      - A tenth run state, or a rename of any of the nine. They are in the SQL schema, in
        every log line and in five layers (01-CONTEXT D-01, one-way).

    Every port you add or change must get its fake updated in the same edit. Phases 2-6
    unit-test against `src/domain/fakes.ts` alone, so a port whose fake does not implement
    it breaks every one of those test files at once.

    `src/domain/` must still import nothing outside itself when you are done.
