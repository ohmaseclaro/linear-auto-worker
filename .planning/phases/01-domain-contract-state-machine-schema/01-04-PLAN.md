<task type="auto">
  <name>Task 1: The migration runner over PRAGMA user_version</name>
  <files>src/infra/store/migrate.ts</files>
  <action>
Implement D-10: schema evolution on SQLite's built-in `user_version` pragma, with numbered
migration modules and no schema_version table of its own. Read the current version, apply every
migration above it in ascending order inside a transaction, bump the version. This is what makes
"run it twice, the second is a no-op" true, and it is why upgrading the daemon on an existing
database does not discard run history or a question still waiting on the operator's reply.

Exports:

- a `Migration` type: a numeric `version`, a `name`, and a `sql` string.
- a `MigratableDb` structural interface describing only what the runner uses: an `exec` taking
  a SQL string, and a `prepare` returning something with a `get`. Type it structurally rather
  than importing the `better-sqlite3` types. That keeps this module runnable against
  `node:sqlite`'s synchronous database in its own test on a branch with nothing installed,
  which is the difference between a test that exists and a test that can ever run.
- `readUserVersion(db)` and `migrate(db)`. `migrate` returns a record of the version it started
  at, the version it ended at, and the list of versions it applied — an empty applied list on a
  second run being the observable form of the no-op.

Implementation notes:

- `PRAGMA user_version` cannot be parameterised, so the new version is interpolated into the
  statement. Assert the value is a non-negative safe integer before interpolating and throw
  `MigrationError` from the domain errors module otherwise. This is the one place in the
  project where a value is concatenated into SQL, and it is guarded rather than trusted.
- Wrap each migration in an explicit begin/commit, rolling back and rethrowing as
  `MigrationError` on failure, so a half-applied migration cannot leave the version bumped.
- Assert the migration list is strictly ascending with no duplicate versions before applying
  anything, and throw `MigrationError` naming the offending version if not. Two migrations
  numbered the same is a merge artefact this project is unusually likely to produce.
- Import `MigrationError` with a `.js` extension on the relative specifier.
- Down-migrations are deliberately absent — they never run in a single-operator local daemon,
  and `user_version` does not preclude adding them later. Say so in a comment so nobody adds
  them back as an oversight.
  </action>

<task type="auto">
  <name>Task 2: The five-table schema as a SQL template literal</name>
  <files>src/infra/store/migrations/001-init.ts, src/infra/store/migrations/index.ts</files>
  <read_first>src/domain/types.ts (the Run, PendingQuestion and RunState declarations)</read_first>
  <action>
Per D-11, write the migration as a TypeScript module exporting its SQL as a template literal,
not as a `.sql` file. `tsc` does not copy non-TS assets, so a `.sql` file would need both a
build copy step and a path resolved off the module url — two things that work under `tsx` in
development and fail with a missing-file error once built. The SQL stays one readable blob
either way.

`001-init.ts` exports a single `Migration` object with version 1, the name `init`, and the SQL
below. `index.ts` exports the ordered `MIGRATIONS` array, typed as a readonly `Migration` array,
containing it.

**Naming rule, and it is load-bearing:** every column name is the snake_case form of the
corresponding field name in `src/domain/types.ts`, with no exceptions and no abbreviations.
Phase 2 writes the real store's SQL on a branch that cannot see this file; that rule is the only
thing that makes both derivations land on the same names.

**`runs`** — id (text primary key), parent_run_id (text, nullable, referencing runs.id), kind
(text, not null, constrained to the ticket and repo literals), issue_id, issue_key, issue_title
and issue_url (all text not null), repo_dir, repo_slug, branch, worktree_path, session_id (text,
nullable), pid (integer, nullable), state (text, nullable, constrained to exactly the nine
`RunState` literals), cancel_requested and resumable (integer, not null, defaulting to 0),
attempt and question_round (integer, not null, defaulting to 0), pr_url and failure_reason
(text, nullable), created_at and updated_at (integer, not null).

Add a table-level constraint encoding D-04: state is null when kind is the ticket literal and
non-null when kind is the repo literal. A parent run row carries no stored state so that parent
and children cannot disagree — the disagreement being the exact bug that would let one repo's
failure discard another repo's already-shipped pull request. Enforce it in the schema rather
than in application code, so no layer can write a parent state by accident. Put that reason in
a SQL comment.

Indexes on runs: state; issue_id; parent_run_id; and a composite over state with created_at for
the queue read.

**`questions`** — id (text primary key), run_id (text not null, referencing runs.id), text and
assumption (text not null), linear_comment_id (text, nullable), asked_at and deadline_at
(integer not null), status (text not null, constrained to the four literals of
`PendingQuestion.status`), answer (text, nullable). Indexes: a composite over status with
deadline_at for the deadline sweep, since question deadlines are absolute timestamps swept by a
scheduler tick rather than in-process timers that would not survive a restart; a composite over
run_id with status; and a unique index on linear_comment_id restricted to non-null values,
because correlation is by stored comment id and a duplicate would make it ambiguous.

**`deliveries`** — delivery_id (text primary key) and received_at (integer not null), with an
index on received_at for pruning. The primary key IS the uniqueness guarantee that the fourth
webhook loop-prevention layer depends on; it must not be a plain column with an application-side
check.

**`kv`** — k (text primary key), v (text not null), updated_at (integer not null).

**`run_events`** (D-03) — an autoincrementing integer primary key, run_id (text not null,
referencing runs.id), from_state (text, nullable — null for the row recording the initial
insert), to_state (text not null), at (integer not null), detail (text, nullable). Index over
run_id with at. Note in a comment that the trigger name goes in detail: D-03 fixes these five
columns and a sixth would drift from it. Name the columns from_state and to_state rather than
the bare words, which are SQL keywords and would need quoting at every use site.

Every statement is `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`, so a partially
applied database is recoverable. Do not set WAL, foreign_keys, or busy_timeout here — those are
connection pragmas and belong to Phase 2.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| migration version value → SQL text | `PRAGMA user_version` cannot be parameterised, so the version is the one value in the project concatenated into a SQL statement |
| Linear delivery id → deliveries table | An attacker-influenceable header value becomes a primary key; the constraint is the last of the four webhook loop-prevention layers |
| Linear issue text → runs table | Issue title, url and branch reach the database as parameters bound by Phase 2's store, never as SQL text |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-15 | Tampering | `migrate` version interpolation | high | mitigate | The only interpolated SQL value in the project. It is asserted to be a non-negative safe integer before use and throws `MigrationError` otherwise, and it originates from a literal in a checked-in migration module rather than from any input. |
| T-01-16 | Tampering | `deliveries.delivery_id` | high | mitigate | Declared as the table's primary key, so replay rejection is a database constraint. An application-side check would race between the lookup and the insert, and the whole point of this column is to be the layer that holds when the other three loop guards have failed. |
| T-01-17 | Tampering | `runs.state` | high | mitigate | A CHECK constraint enumerating exactly the nine `RunState` literals, so a layer that writes a state the machine does not know fails loudly at insert rather than parking a run in a state nothing can transition out of. |
| T-01-18 | Repudiation | transition history | medium | mitigate | `run_events` (D-03) records every transition with its from-state, to-state, time and detail, so a transition that failed to log is a missing row that restart recovery and the terminal comment both notice, rather than a missing log line nobody greps for. |
| T-01-19 | Elevation of Privilege | parent/child run reconciliation | high | mitigate | The table constraint makes a stored parent state unrepresentable (D-04), so no layer can write a parent status that contradicts its children and discards a sibling repo's shipped pull request. |
| T-01-20 | Information Disclosure | database file location | low | transfer | The database lives under the config root (D-06) with the daemon's other state. Directory creation and file permissions belong to Phase 2 and the Phase 8 wizard. |
</threat_model>
