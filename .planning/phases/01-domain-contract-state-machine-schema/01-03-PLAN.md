<naming_contract>
`research/ARCHITECTURE.md` § "The rule that makes this actually work in parallel" names seven
of these fakes: `InMemoryStore`, `FakeLinearClient`, `FakeAgentRunner`, `FakeWorktreeManager`,
`FakeDeliverer`, `RecordingNotifier`, `FakeTunnel`. Those seven names are fixed — sibling
phases are writing `import { InMemoryStore } from '../domain/fakes.js'` today. The remaining
seven follow the same convention: `FakeConfigLoader`, `RecordingLogger`, `FakeWebhookRegistrar`,
`FakeReceiver`, `FakeEventRouter`, `FakeScheduler`, `FakeRunEngine`.

Note `FakeTunnel`, not `FakeTunnelManager` — ARCHITECTURE.md wrote it short and a rename breaks
Phase 3.

Everything is a plain class with a public constructor taking optional seed data and no
arguments required. Nothing here touches the filesystem, the network, a timer, or a child
process — a fake that needs a tmpdir is not usable from a unit test written on a branch with no
dependencies installed.
</naming_contract>

Create fakes.ts and implement the three L0 fakes. Import types and interfaces from
`./ports.js` and `./types.js` with `.js` extensions and the type-modifier import form.

**`InMemoryStore` implements `Store`** — Maps keyed by id for runs, questions, deliveries and
kv, plus insertion-order preservation so the queue reads back in the order rows arrived.
Implement every method the interface declares, and specifically:

- `nextQueued(limit)` returns queued repo-kind runs ordered by createdAt ascending, capped at
  limit. Phase 6's scheduler is tested against exactly this.
- `listByState(...states)` and `findActiveRunByIssue(issueId)` — the latter returns only
  non-terminal runs, using `isTerminal` from `./state-machine.js` rather than a hand-written
  list, so a state added later cannot silently drop out of the filter.
- `childRuns(parentId)` returns the runs whose parentRunId matches.
- `recordDelivery(deliveryId, receivedAt)` returns false when the id is already present and
  true when it was inserted, with no other effect either way. This mirrors the real
  implementation's insert-or-ignore-then-check-changes semantics; a test-only version that
  looked the id up first and then inserted would model a race the real store is specifically
  written to avoid, and would teach Phase 3 the wrong contract.
- `pruneDeliveries(olderThan)` drops entries with an earlier receivedAt.
- `findQuestionByCommentId` and `findQuestionByShortCode` — correlation by stored comment id
  and by the short code, never by recency.
- `expiredQuestions(now)` returns open questions whose deadlineAt has passed. Deadlines are
  absolute timestamps compared against the `now` the caller passes; the fake takes no clock of
  its own so a test can drive time without waiting.
- `transaction(fn)` runs the function and returns its value; on a throw, restore the maps to
  the snapshot taken at entry so a failing transaction leaves no partial write. Snapshot by
  copying the Maps — the data volume in a unit test makes anything cleverer pointless.
- `close()` is a no-op.

**`FakeConfigLoader` implements `ConfigLoader`** — constructed with an optional partial config
merged over a built-in default. The built-in default must exercise the CONF-01/CONF-02 shape
rather than being a stub: a `defaults` block with all six toggles populated, and a `mappings`
array holding at least one project-keyed mapping with two repos and a slack webhook url, plus
one team-keyed mapping (D-07's fallback path) carrying a sparse `overrides` naming exactly one
toggle (D-09). Five layers will use this default as their fixture; if it does not contain a
sparse override, nobody's test ever exercises `resolveToggles`.

**`RecordingLogger` implements `Logger`** — keeps every call as a record of level, bindings,
object and message on a public array, and `child(bindings)` returns a new instance sharing that
array with the parent's bindings merged in. Phase 2's success criterion is that no line
anywhere contains an API key or an authtoken; a logger that discards its input cannot be used
to assert that.

Append the L1 and L2 fakes.

**`FakeTunnel` implements `TunnelManager`** — `open(port)` records the port and resolves to a
fixed https url; `url()` returns it, or null before open and after close; `close()` clears it.
Track an `openCount` so Phase 3's "restarting the worker ten times leaves exactly one tunnel"
test has something to assert against.

**`FakeWebhookRegistrar` implements `WebhookRegistrar`** — `reconcile(publicUrl)` records the
url, increments a `reconcileCount`, and resolves to a stable webhook id and secret. Repeated
calls return the same id, because idempotent create-or-update is the property Phase 3 is
testing and a fake that minted a new id per call would make a passing test wrong.
`disable()` sets a flag.

**`FakeReceiver` implements `Receiver`** — `listen(onDelivery)` stores the callback and resolves
to a fixed port number; expose a public `deliver(d)` helper that invokes the stored callback, so
a test can push a `WebhookDelivery` through the seam without an HTTP server. `setSecret` records
the secret; `close()` clears the callback.

**`FakeEventRouter` implements `EventRouter`** — constructed with a queue of `DomainEvent`
values to return in order, falling back to the ignored variant once the queue is drained.
Record every delivery it was handed.

**`FakeScheduler` implements `Scheduler`** — a real counting semaphore over an in-memory
capacity (default 3, matching the project's concurrency cap), because the property Phase 6 must
test is that a run parked awaiting an answer holds no slot and that three parked questions
leave all three slots free. `acquire(runId)` resolves when a slot is free and returns a release
function that is idempotent — releasing twice must not hand out a slot that was never taken.
`inUse()` and `capacity()` report honestly; `start()` and `pause()` toggle a flag.

**`FakeRunEngine` implements `RunEngine`** — records the events passed to `handle`, the ticks,
and whether `recover` and `drain` were called. It exists so Phase 3 can test that its router
hands the right domain event to the engine without the engine existing.

**`FakeWorktreeManager` implements `WorktreeManager`** — an in-memory map from runId to a
`Worktree` value. `create` synthesises a path string under a fixed root without touching the
filesystem; `remove` deletes the entry; `exists` reads the map; `gc(liveRunIds)` removes and
returns the paths of entries whose runId is not in the set.

**`FakeAgentRunner` implements `AgentRunner`** — constructed with a scripted array of
`AgentResult` values, returning them in order and repeating the last one once exhausted. This
is the fake that makes the whole Q&A round trip testable with no Claude process and no network:
scripting a needs-input result followed by a complete one drives a run from running through the
parked state and back. Record each `AgentSpawnRequest` it received so a test can assert that a
resume carried the right session id and the resume flag. Honour the `AbortSignal`: if the signal
is already aborted, or aborts while pending, resolve to the cancelled variant rather than
throwing — a cancellation is an outcome here, not an error. `onProgress` stores the callback and
a public helper emits a line through it.

**`FakeDeliverer` implements `Deliverer`** — returns a synthetic pull request url and number,
recording every call. On a repeated call for the same worktree, return the same pull request
rather than a new one; the interface documents delivery as idempotent and a fake that minted a
second PR would hide a double-delivery bug rather than surface it.

**`FakeLinearClient` implements `LinearClient`** — an in-memory issue map seeded through the
constructor. `viewer` returns a fixed bot identity; `getIssue` reads the map and throws
`LinearApiError` on a miss; `listAssignedOpenIssues` filters on assigneeId; `setIssueState`
records the transition; `createComment` appends to a public comments array and returns a
generated id — the id must be returned and retained, because question correlation depends on
the stored comment id and never on recency. The four webhook CRUD methods operate on an
in-memory webhook list.

**`RecordingNotifier` implements `Notifier`** — appends every `RunEvent` to a public array and
never throws, ever, under any circumstance. Its real counterpart's contract is that a
notification channel failing never fails the run; a fake that can throw teaches the opposite.

**`src/domain/fakes.test.ts`** — a `node:test` file that constructs every fake with no
arguments and asserts a single meaningful behaviour of each: the store returns false on a
duplicate delivery id and true on a fresh one; the scheduler hands out exactly its capacity and
then blocks, and a doubled release does not inflate the count; the agent runner returns the
scripted results in order; the notifier retains what it was given; the config loader's fixture
resolves a sparse override over the defaults. Constructing every fake in one file is what turns
"a compiling fake for every port" into something the integration gate actually checks. Write
the file; do not run it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| (none crossed at runtime) | Every fake is in-memory and test-only: no filesystem, no network, no child process, no timer. The boundary that matters here is epistemic — a fake whose semantics differ from the real implementation teaches five parallel layers a false contract. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-10 | Tampering | `InMemoryStore.recordDelivery` | high | mitigate | The fake returns false for an id already present and true otherwise, with no read-then-write gap, mirroring the real store's insert-or-ignore-then-check-changes semantics. Modelling it as a lookup followed by an insert would teach Phase 3 a delivery-dedupe contract that races, and delivery dedupe is the last of the four webhook loop-prevention layers. |
| T-01-11 | Denial of Service | `FakeScheduler` | high | mitigate | A real counting semaphore with an idempotent release, so Phase 6's test that three parked questions leave three slots free measures something. A permissive fake would let the slot-leak defect ship undetected to the integration gate. |
| T-01-12 | Information Disclosure | `RecordingLogger` | medium | mitigate | Retains every line so Phase 2 can assert that no output contains an API key or an authtoken. A discarding logger makes that success criterion untestable. |
| T-01-13 | Spoofing | `FakeLinearClient.createComment` | medium | mitigate | Returns and retains a distinct comment id per call, so question correlation is exercised against the stored id rather than against recency — the correlation that breaks the moment two runs are open on one ticket. |
| T-01-14 | Tampering | fakes shipped in the production module graph | low | accept | `fakes.ts` sits inside `src/domain/` and is re-exported by the barrel, per the ADDENDUM's module list. This is a locally-run single-operator daemon with no bundler and no published package, so the cost is a few unused kilobytes. |
</threat_model>
